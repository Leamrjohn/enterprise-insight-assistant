# 收尾工单 $ARGUMENTS

## 1. 核对验收

- 找到完整计划里这个工单的“怎么验收”，逐条对照**本次实际运行的结果**。
- 没运行过的验证项，就写“未验证”，不要写“通过”。
- 有验收没达到时，结果写“部分完成”或“失败”，不要为了收尾改测试期望。

## 2. 记录（AGENTS.md 文档规则）

- `docs/worklog.md` 末尾加一节 `## <日期> <工单号> <名称>`，**最多 5 行**：做了什么、验证结果（命令加通过和失败数）、遗留问题或待办。
- `docs/STATUS.md` 末尾加一行：`- <日期>：<工单号> <一句话结果>；<验证摘要>。`
- 不要追加 `docs/history/evidence.md`（已冻结）。

## 3. 提交（只提交本工单的文件）

1. 运行 `git status --short`，把文件分成两组：本工单改的，和其他的（包括开工前就有的未提交改动）。
2. 只 `git add` 本工单的文件，以及 worklog 和 STATUS。**不要用 `git add -A` 或 `git add .`。**
3. 不确定某个文件是否属于本工单时，问用户。
4. 提交信息一句话，中英文均可，末尾带当前会话要求的署名行。
5. 不推送；不改写历史。

## 4. 汇报（中文，不超过 30 行，按 AGENTS.md 格式）

- **结果：** 一句话，成功 / 部分完成 / 失败。
- **改了什么：** 文件名加一句话说明。
- **怎么验证的：** 命令加真实输出摘要（通过几个、失败几个）。
- **没验证到的：** 明确列出。
- **学习笔记（不超过 10 行）：** 症状 → 根因 → 调用链（函数 A 调用函数 B，传了什么）→ 为什么这样设计。术语第一次出现时用一句话解释。
- **下一步建议：** 最多 2 条，优先写完整计划里排在它后面的工单。

不要使用“生产级”“已完成”“稳定”这类词，除非有本次运行的证据。
