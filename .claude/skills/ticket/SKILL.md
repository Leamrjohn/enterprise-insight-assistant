# 开始工单 $ARGUMENTS

按下面顺序做，**第 4 步之前不改任何文件**。

## 1. 读规则和工单（只读这些）

1. `AGENTS.md`（如果本会话已经加载过，不要重读）。
2. `docs/design/complete_plan_2026-11-07.md`：第 2 节，以及第 5 节里包含工单 `$ARGUMENTS` 的那一段。用 Grep 找到 `| $ARGUMENTS ` 所在的行和它所在的段，不要通读全文。
3. `docs/design/enterprise/` 里对应模块的设计，只读和 `$ARGUMENTS` 有关的段落（用 Grep 定位）。
4. `docs/STATUS.md` 最后 10 行，`docs/worklog.md` 里和这个工单或它的前置有关的记录（用 Grep）。

找不到这个工单号时，停下来告诉用户，并列出当前段（AGENTS.md“当前段”）里的工单。

## 2. 核对能不能开工

- **段：** 工单所在的段是否就是 AGENTS.md 写的当前段。不是就停下，问用户是否插队。
- **前置：** 段落“怎么做”里排在它前面的工单，以及表格“批准”列和第 5 节“硬依赖”里提到的前置，是否在 STATUS 或 worklog 里有完成记录。没有就停下说明。
- **工作区：** 运行 `git status --short` 和 `git branch --show-current`。分支应符合 AGENTS.md 的分支规则；有和本工单无关的未提交改动时，列出来，开工时不要动它们。

## 3. 向用户复述（不超过 10 行）

- 工单号、名称、分工（训练 / 共建 / 代做）。
- 目标：2～3 行。
- 验收标准：照抄完整计划里该工单“怎么验收”一列；如果写着“第 4 步定”，提出一个具体数值请用户确认。
- 需要批准的事项：改表、新依赖、付费运行、改主链或权限、改测试期望、超过 10 个文件或 400 行。每项附上你的推荐。
- 预计要读和要改的文件（不超过 5 个）。

有需要批准的事项时，**等用户回复再继续**。

## 4. 开工

- **训练工单：** 按 AGENTS.md 的放手阶梯。先问用户在哪一层（看懂 / 补全 / 主导），不确定就从“补全”开始：你给骨架、测试和失败现象，用户写关键的 5～30 行，你只评审。
- **共建工单：** 用户已确认方案后由你实现。
- **代做工单：** 直接完成。
- 按 AGENTS.md 工作流程：先复现，再修改，再验证；验证从针对性测试开始。

结束时用 `/wrap-ticket` 收尾。
