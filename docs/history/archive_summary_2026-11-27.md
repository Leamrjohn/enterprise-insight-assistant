## 2. 11 月 5 日的现状评估（企业级总计划第 1 节）

当时的判断：**安全控制已经比较严格，但工具、记忆、上下文的能力是为少数场景写死的。**

| 模块 | 当时水平 | 主要依据 |
|---|---|---|
| SQL 防线 | 接近企业级 | AST、Schema、只读事务多层拦截；54 种攻击全拦 |
| 确定性发布 | 接近企业级 | 发布由代码决定，Reviewer 不能替代 |
| 任务可靠性 | 单机较好 | 租约、令牌、检查点、Outbox；并发只有 1 |
| 模型账本 | 较好 | 调用前预占、未知费用单独计；只有任务级预算 |
| 工具 | 能力 demo，治理较好 | 3 个工具写死在多张表；主链不让模型选工具 |
| 记忆 | 分层是空壳 | 表支持 4 层，实际只写 `fact` |
| 上下文 | demo | 只有证据复核 1 个节点接入，超预算照发 |
| 提示词 | demo | 模板散在函数里，`prompt_version` 1302/1302 为空 |
| 模型网关 | 基础可用 | 全局一个模型和温度，备用模型列表为空，无熔断 |
| 配置 | 基础可用 | 约 87 个平铺字段，写错名字不报错 |
| 身份和租户 | 有明显缺口 | 限流可绕过，无登录失败限制，核心表无 RLS |
| 可观测 | 基础可用 | 有日志和 trace 脚本，没有指标和告警 |
| 工程化 | 有底子未闭环 | 工作分支 255 个提交不在远程，从未进 CI |
| RAG | 评测好，上线未完成 | `passage_v1` 切换两次未过验收 |
| 前端 | demo | 10 个源文件，依赖写 `latest`，无端到端测试 |

其中上下文、提示词、配置、可观测、工程化已在 R1、R2 改造；其余在 R3 之后。

## 3. P0 评测基线（11-02）

- **上下文：** Data 节点平均输入 2027 token、输出 192 token；每次提供 22 张表，24 道 SQL 题平均只用 1.75 张、最多 3 张。
- **SQL 波动：** 当时录制 4 轮 24 题，首轮 22 通过、放行错误数字 0。
- **RAG：** 153 篇语料加 16 篇陷阱文档，64 题；现行策略（段落 + 向量 + 重排）Hit@3 0.719、Recall@3 0.690、MRR 0.711、找到答案 73.3%。
- **记忆：** 选择结果和问题完全无关，永远是最近的 8 条；公司和用户隔离、撤销和过期都生效。

## 4. 11-02 故障演练结果

| 故障 | 结果 |
|---|---|
| 规划阶段杀 Worker | 约 2 分钟后第 2 个执行接管并完成；被打断的调用记为未知费用 |
| Redis 停止时提交 | 任务入库、Outbox 等待，Redis 恢复 19 秒后完成 |
| 运行中停 Redis 30 秒 | 任务照常完成 |
| 运行中重启 PostgreSQL | **直接失败、未重试**（PendingRollbackError），后续工单修复 |
| 模型超时 1 秒 | 超时在受理时冻结进任务，只改 Worker 无效（设计如此） |
| 2 个 Worker 加 3 次重复投递 | 只有 1 个执行，无冲突 |
| 运行中取消 | 已取消、无报告、取消后 0 次调用 |

## 5. SQL 五层防线（11-02 调查）

1. 契约：只允许单条 SELECT。
2. AST：表白名单、禁止 schema 前缀。**当时 27/54 种攻击能通过**（CTE 里的写操作、FOR UPDATE、危险函数等），之后修复到 54/54 全拦。
3. 范围：经营库行级安全加公司快照。
4. 执行：只读连接、只读事务、语句超时、行数上限；分析账号非超级用户、无写权限。
5. 审计：工具调用记录和事件（SQL 原文不进审计）。

## 6. 旧路线图的目标数值（roadmap 00 第 5 节）

“接近生产级”的定义：像对待真实线上系统一样设计、测试、演练和记录；**不做**多机高可用、Kubernetes、真实流量 SLO、合规认证、真实客户数据。

- 固定冒烟集（8 题 × 3 次）成功率：中期 ≥ 90%，终验 ≥ 95%。
- 硬门禁 H1～H7 始终为 0；故障演练全部通过。
- 检索 Recall@5 初始期望 ≥ 0.85。
- 端到端 P95 耗时和单任务费用不超过基线的 1.5 倍。

## 7. 更早计划里仍然有效的原则

- **外层受控编排、内层模型驱动工具循环：** 模型提出调用，受信任的运行时校验并执行；模型不直接拿到数据库连接或执行权。（架构重构需求，10-07）
- **生产级设计 = 明确的不变量、失败行为、资源预算、恢复方式和验证证据。** 单机能验证这些机制，但不能证明高可用和企业流量。（核心审计，09-15）
- **现有架构适合继续改造，不需要换框架或推倒重来。**（核心审计，09-15）
- **依赖方向：** 接入和控制层 → Agent 层 → 平台层 → 数据层，现在由 import-linter 强制。（目录结构，10-19）
