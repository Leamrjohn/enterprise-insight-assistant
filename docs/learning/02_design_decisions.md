# 02 设计决策记录：每一步的意义、备选方案与取舍

每条按同一格式：**问题** → **意义**（不做会怎样） → **备选方案** → **选择与理由** → **代价**。
执行细节见 [01_execution_record.md](01_execution_record.md)。

---

## D1 补充计划而不是重写计划

- **问题**：已有 00～03 路线图，但缺少用户最想学的几项（模型选工具、提示词、组件评测）。
- **意义**：计划是验收标准的来源；缺项意味着这些能力永远不会被系统地做和测。
- **备选**：①推倒重写；②只在 00 里加几行；③新增补充文件 04，00 只加指引。
- **选择**：③。00～03 的硬门禁和规则经过多轮使用，重写会丢失；04 让新增内容可以单独审阅。
- **代价**：读计划要看两处；用“冲突时以 04 为准”化解。

## D2 日志：在格式化器统一脱敏，而不是在每个调用点脱敏

- **问题**：日志里出现密钥、手机号；排错时无法按任务串日志。
- **意义**：日志会被复制、转发、长期保存，泄漏面远大于数据库；没有关联编号，排一个任务要人工拼时间线。
- **备选**：①每处 `logger.info` 前手动脱敏；②在格式化器（唯一出口）统一脱敏；③日志采集侧（如 Fluent Bit）脱敏。
- **选择**：②。只有一个出口，新代码不需要“记得”脱敏；③需要额外组件，单机项目收益小。
- **代价**：正则可能误伤（例如长数字串被当成手机号）；脱敏规则只覆盖已知格式，不是通用个人信息识别。

## D3 关联编号用 ContextVar 自动带上

- **备选**：①每次打日志手动传 `extra={"task_id": ...}`；②ContextVar（上下文变量）在任务入口设置一次，格式化器自动读取；③OpenTelemetry 全链路追踪。
- **选择**：②。改动最小、不会漏；③是生产常用方案，但要引入新依赖（需用户批准），可作为后续升级。
- **代价**：跨线程/跨进程不会自动传递，需要在新的执行入口重新设置（Worker 入口就是这样做的）。

## D4 部署检查不能只看测试

- **问题**：2.3 离线测试全绿，但部署后发现 Worker 日志根本没走项目格式化器。
- **意义**：测试证明“函数对”，部署检查证明“系统真的在用这个函数”。
- **备选**：①只看测试；②部署后在真实容器里写一条探针日志并检查输出；③写端到端测试启动真实 Worker。
- **选择**：先做②，并把发现转成单元测试（信号接收器存在且调用 `configure_logging`），防止回退。③成本高，留到阶段 9 的 CI 分层。

## D5 Outbox 竞态：让“认领成功”决定事件状态

- **问题**：Worker 比 API 记录 `broker_accepted` 更快时，事件永远停在 `broker_accepted` 并被反复发布。
- **意义**：浪费队列与数据库资源；如果哪天 Worker 不幂等，会产生重复执行（违反硬门禁 H4）。
- **备选**：
  1. API 在发消息前先把状态写成 `broker_accepted`（先记后发）——但发失败时要回滚，状态更复杂；
  2. Worker 认领前等待事件变成 `broker_accepted`——引入等待和超时，拖慢所有任务；
  3. 用数据库行锁让 API 与 Worker 串行——增加锁竞争和死锁风险；
  4. **认领可以从任意未认领状态推进**，并在重投递遇到终态任务时关闭残留事件。
- **选择**：4。Worker 成功认领是“确实送达”的唯一可靠证据；它不依赖两个进程谁先完成。残留事件靠下一次重投递自愈，不需要手工改库。
- **代价**：API 的 `mark_broker_accepted` 此时会返回 False（事件已被认领），调用方必须能接受；已检查调用方不依赖该返回值。
- **前提**：所有创建事件的地方都在同一事务里把任务置为 queued（已逐一核对三处）。

## D6 评测“先免费、后付费”

- **意义**：付费评测一次几分钱，但每次改代码都跑就会持续花钱，而且结果受模型随机性影响。
- **备选**：①全部用端到端冒烟；②组件评测直接调用真实模型；③免费的确定性/本地模型评测先做，付费部分录制一次后离线回放。
- **选择**：③。检索（本地模型）、报告校验（纯代码）完全免费；路由与 SQL 录制一次后，下游代码改动都能免费复测。

## D7 检索评测用真实问题、文档级相关性

- **问题**：已有慢测试用“从文档里抽客户名生成问题”的模板，问题里直接带关键词，偏简单；且只认一篇相关文档。
- **备选**：①沿用模板问题；②用夹具里的真实业务问题与 `document_scope`；③人工标注 chunk 级金标准。
- **选择**：②作为本次基线，并保留①的慢测试作对照。③最准确但需要人工逐条标注，列为后续。
- **代价**：真实问题只有 19 个（留出 4 个），统计波动大；文档级命中不代表答案正确。

## D8 报告校验评测要核对“拦截原因”

- **问题**：首版评测 100% 拦截，但部分是因为样例缺字段，被无关规则拦下。
- **意义**：只看“有没有拦”会把评测本身的错误当成系统的优点——这是评测里最常见的陷阱之一。
- **选择**：每个篡改只破坏一条规则，并登记预期原因；原因不符不计拦截。同时放入合法对照，统计误拦率。

## D10 审计事件序号：保存点重试而不是行锁

- **问题**：多个投递同时给同一执行追加事件，“最大序号 + 1”撞唯一约束。
- **备选**：①`SELECT ... FOR UPDATE` 锁住执行行再算序号；②PostgreSQL 序列（sequence）或自增列；③保存点内插入，冲突就重试；④咨询锁（advisory lock）。
- **选择**：③。①的风险是：Worker 可能追加事件后、提交前进行长时间模型调用，此时行锁一直被持有，心跳线程更新同一行会被阻塞，租约过期后任务被别人接管——修一个小问题引出大问题。②会让每个执行内的序号不再从 0 连续，改变已有语义且要迁移。④同样会让落败者等到获胜者提交。
- **代价**：极端高并发下要重试几次；上限 5 次后抛出明确错误。

## D11 重试抖动用 [0.5, 1.5] 倍

- **备选**：①不抖动；②“完全抖动” `random(0, base)`；③“等量抖动” `base/2 + random(0, base/2)`；④本次的 `base × (0.5 + random)`。
- **选择**：④。平均等待仍是原来的 base，不改变整体节奏；最短也有一半 base，避免②那种几乎立即重试再次撞上限流。
- **背景**：多个任务同时被模型服务限流（429），如果都在同一秒重试，会再一起被限流，这叫“惊群”。

## D12 暂不加任务级墙钟截止时间

- **现状**：单步有超时、图有 20 步上限、执行有租约；所以一个任务的总时长已经被“步数 × 单步上限”间接限定。
- **备选**：①Celery `soft_time_limit`；②在图的每个节点前检查截止时间；③维持现状。
- **选择**：③，并用测试锁住步数上限。①会在任意代码位置抛异常，可能打断数据库写入；②要改主链所有节点（按规则需用户批准）。
- **何时该加**：如果出现“每步都不超时、但总时长不可接受”的真实案例。

## D13 检索基线后先记录问题、不立即修

- **发现**：重排无增益且慢 110 倍；双切块合并丢失重叠加权。
- **为什么不立刻改**：阶段 6 的规则是“一次只改一个变量，每次对比基线”；19 题样本太小，直接关掉重排可能是被小样本误导。正确做法是先扩充评测集，再逐个变量对比。

## D14 付费评测自带费用闸门

- **问题**：评测脚本直接调用模型时没有任务上下文，项目的预算治理不生效。
- **备选**：①临时造一个任务行，借用现有预算治理；②只靠人工估算；③脚本内包一层“调用前预估最坏费用”的闸门。
- **选择**：③。①要往运行库写数据、混进业务统计；②出错时没有任何保护。③在调用发生前就拒绝，最坏情况也不会超过上限。
- **代价**：预估值不是供应商账单；需要事后核对。

## D15 评测标签有疑问时不擅自修改

- **问题**：路由准确率 64%，其中一部分是标签本身不适合组件评测。
- **意义**：改标签能让数字立刻变好看，但这正是“为了通过而改期望值”，项目规则明确禁止。
- **选择**：保留原始 64% 作为基线，同时给出人工归类（不适合 5、可争议 6、明确错误 3），由用户决定是否另建一份“路由专用标签集”。

## D16 路由专用标签：可接受集合 + 规则编号

- **问题**：原标签里混有不适合组件评测的题和本身有两种合理答案的题。
- **备选**：①直接把原标签改成模型答案；②每题只允许一个“正确答案”，重新人工判定；③保留原标签为首选，按书面规则增加“也可接受”的答案，并排除不适用的题。
- **选择**：③。①是为通过而改期望；②在真有歧义时会制造新的争议。③让每个放宽都可追溯到一条规则，审阅者可以逐条否决。
- **防偏差措施**：规则先写、后套用；对所有符合规则的题一律适用（包括模型原本答对的题）；原标签保留；状态标为待确认。
- **局限**：标注者已看过模型输出，无法完全消除偏差。更严格的做法是由没看过模型输出的人独立标注，再比较两人一致率。

## D17 演练中发现问题先记录、不当场修

- **问题**：数据库重启演练暴露“短暂中断 → 永久失败”。
- **备选**：①当场把 PendingRollbackError 加入可重试；②记录现象与调用链，另立工单先写复现测试再修。
- **选择**：②。PendingRollbackError 只说明“之前有个数据库错误没回滚”，原因可能是连接中断（应重试），也可能是唯一约束等永久错误（不应重试）；当场放宽会把永久错误也重试。演练的职责是暴露问题，修复要走“复现 → 修改 → 验证”的流程。

## D18 超时等运行参数在受理时冻结

- **现象**：只改 Worker 的超时不影响已受理的任务。
- **意义**：运行参数（超时、预算、输出上限）在任务受理时写入任务快照，执行过程中配置被改也不会改变一个正在跑的任务的规则——结果可复现、费用可预期。
- **代价**：演练或紧急调整时要同时改受理方（API），而且只对新任务生效。

## D19 基础设施错误不能被业务层吞掉；按异常链判断根因

- **问题**：Planner 的兜底 `except Exception` 把数据库断连变成“Planner 业务失败”，工作流以为是不可重试的规划错误。
- **备选**：①在每个 Agent 里分别处理数据库错误；②提供一个共享判断函数，业务层遇到短暂数据库错误就向上抛，由 Worker 统一回滚和决定重试；③把 PendingRollbackError 一律当成可重试。
- **选择**：②，并沿 `__cause__`/`__context__` 找根因。③会让唯一约束这类永久错误也被重试。
- **为什么要看异常链**：真实故障里第一个错误常被“处理它的代码”产生的第二个错误盖住（网关在异常分支里写调用记录又失败了）。只看最外层异常会误判。
- **兜底**：数据库长时间不可用时，连“标记 retrying”都写不进去；这时靠执行租约过期后的恢复任务接管——所以租约机制不能删。

## D20 AST 层用函数“黑名单”而不是“白名单”

- **备选**：①白名单：只允许 sum/count/round 等列出的函数；②黑名单：拒绝 pg_*/lo_*/dblink*/txid_* 前缀和 set_config 等；③不在 AST 层管函数，全靠数据库权限。
- **选择**：②。①最安全，但模型合理使用新函数（如 date_trunc、percentile_cont）就会被误拦，需要先扩充评测样本再收紧；③违背“每层独立成立”的纵深防御原则。
- **防误拦**：用 45 条历史真实 SQL 做回归；以后扩充 SQL 评测（2.5.6）时可以考虑升级为白名单。
- **为什么执行层已经兜住了还要改 AST**：数据库权限可能被误配（例如某天换成了 owner 账号连接）；AST 层是代码里可测试、可审查的一道独立防线。

## D21 多余工具参数：保留“丢弃后继续”

- **备选**：①拒绝（严格契约，便于发现调用方错误）；②丢弃后继续（宽进严出）。
- **选择**：保留原设计②。服务端控制参数（超时等）总是在校验之后由服务端注入，所以丢弃不会留下漏洞；原设计有 3 个测试明确约定这种行为。为了自己的偏好改掉已有测试期望，违反“不为通过而改期望”的规则。
- **何时重新考虑**：阶段 4.5 让模型自己组织工具参数时，可以在审计里记录“被丢弃的参数名”，用数据判断模型是否经常传错。

## D9 录制回放：失败即关闭

- **备选**：回放缺失时①自动调用真实模型补录；②直接报错。
- **选择**：②。①会让“免费评测”在提示词变化后悄悄变成付费运行，违反“批量调用模型先申请”的规则。
- **代价**：提示词一改就要重新录制；这是有意的——提示词变化本来就需要重新评测。

## D22 执行层测试：故意关掉 AST 层、连真实数据库
- **备选**：①用模拟数据库连接做单元测试；②连真实演示经营库，并把 AST 校验替换成空函数。
- **选择**：②。只读事务、角色权限、statement_timeout 都是 PostgreSQL 自己执行的，模拟连接只能测“代码有没有发出 SET 语句”，测不到“数据库有没有真的拒绝”。关掉 AST 层是为了证明执行层**单独**成立，否则攻击会先被 AST 拦下，执行层等于没被测。
- **安全边界**：写尝试全在事务内回滚、从不提交；连接只用只读账号。
- **代价**：需要演示库运行和一个环境变量；没设置时整个模块跳过（而不是失败），所以 CI（阶段 9）必须显式注入，否则这些测试会“静默不跑”。

## D23 模板查询路径：账号已无写权限，仍加只读事务
- **备选**：①维持现状，只靠账号权限；②加只读事务；③再换一个权限更小的账号。
- **选择**：②。只改两行，与另一条路径一致，账号权限被误配时还有一层。③没有必要：`business_readonly` 已经是只读账号。

## D24 SQL 评测：比较结果数值，并且先提交答案再调用模型
- **备选**：①比较 SQL 文本；②比较结果指纹（校验值）；③运行人工参考 SQL，按数值比较结果。
- **选择**：③。同一个问题有多种正确写法，比较文本会误判；指纹对列名和结构敏感，且现有真实样本太少。③允许别名和多余列不同，只看业务结果。
- **防作弊**：标准答案在录制前提交到 git，提交历史能证明答案没有照着模型输出改。
- **把“正确拦截”和“过度拦截”分开**：只看通过率会把两者混在一起，所以把被拦 SQL 再跑一遍做诊断，但不改变评分。

## D25 过度拦截：补登记指标，而不是放松校验
- **备选**：①补登记口径明确的指标；②允许不声明指标的查询直接放行；③去掉指标校验。
- **选择**：①。②让模型自己决定是否受校验，它可能为了绕开“已交付”条件而不声明指标；③等于取消防线。
- **代价**：未登记的问题仍答不了，例如“无订单客户数”。是否开放②，要配套防绕过规则，留给用户决定。
- **COALESCE**：SUM 没有数据时返回空，改写成 0 会把“查不到”说成“销售额为 0”，所以校验拒绝。COUNT 的 0 是真实结果，不受影响。

## D26 暂不开放未登记指标的查询（用户决定，2026-11-02）
- **选择**：继续拒绝。代价是未回款余额、无订单客户数这类问题暂时答不了，但不会多出一条绕开指标校验的路径。
- **何时重新考虑**：真实使用中这类问题频繁出现时。届时先设计防绕过规则，再用 SQL 结果评测验证。

## D27 检索答案用“文本包含”，不用片段编号
- **备选**：①标注片段编号；②标注答案原文，检查检索片段是否包含。
- **选择**：②。切块策略一改，片段编号就全变，标注会作废；答案原文不受影响，还能比较不同切块策略。
- **代价**：答案短时可能误命中（如“95%”），所以同时看文档级命中。

## D28 新旧版本陷阱用评测专用文档
- **问题**：现有语料没有成对的新旧版本，而且头部日期和正文日期可能不一致。
- **选择**：写 16 篇虚构制度文档，只在回滚事务里建索引，不写入 `data/`。真实语料保持不变。
- **代价**：虚构文档比真实文档规整，结果可能偏乐观，P1 之后要用真实版本文档再验证。

## D29 有效期只能由人登记，不从文档日期推断

文档头部日期是报告日期，常常不等于有效期。未登记的文档不过滤，因为把它们当失效会让检索大面积失效。代价是保护范围只覆盖登记过的文档。

## D30 时间窗口由代码解析，判断不清时放宽

判断错误会悄悄把失效规则交给报告，所以不交给模型。问题里既有历史日期又有“现在”时，新旧版本都取，并把有效期标在证据上，由后面的步骤判断。

## D31 用 RRF 合并两路召回

向量分和全文分尺度不同，不能直接相加。RRF 只看名次，不需要调权重。

## D32 重排分按单片段过门槛，不取平均

重排分两极分化，一条好证据会被无关片段的平均分拖垮。诊断：54 道已检索到答案的题，平均分规则错拒 11 道，新规则错拒 1 道；无答案题通过数从 1 道变为 2 道。

## D33 逐句检查由模型判断含义，代码有最终决定权

模型没给结论、格式错误、引用不存在、被引文档不在所问时段内，都按不通过处理。`applies_to` 是自由文本，代码核对不了，目前只靠模型判断。

## D34 选表只影响提示词，不确定就放宽

校验器始终用完整目录。没匹配到词、SQL 重试、模型判断“结构不够”时都恢复完整结构，因为漏表的代价远大于几百个 token。

## D35 提示词改动必须同期跑对照

同一提示词隔几小时结果就可能不同，和历史数字比会得出错误结论。

## D36 规划器提示词保持原样

问题放末尾、去空段平均少对 1 题，只省约 1.6% 的总 token，所以撤回。这是计划第 4 条在规划器上的例外。

## D37 长对话约束由代码原样保留

用关键词找、不做模型摘要，这样用户的原话不会被改写。代价是其他说法识别不到。约束只能缩小范围，不能改规则或权限。

## D38 记忆先硬过滤，再算相关性

公司、用户、状态、有效期由代码决定，相关性只负责排序。这样再相关的记忆也越不过权限和状态。

## D39 模型只能标记，人决定去留

模型标记后记忆立即暂停，只有管理员能恢复、撤销或替换。替换只能指向另一条已验证的记忆，接口不接受手写内容。

## D40 模型的矛盾标记由代码把关

空结果不算矛盾，记忆里的数字都在结果里也不算矛盾。提示词管不住随机性：只改提示词时，3 轮仍然误标 1～2 次。

## D41 暂不做嵌入向量和其他记忆层

关键词相关性已满足 8 个场景，没有数据说明需要向量。偏好和经验层没有已验证的写入来源，所以只留字段。

## D42 模型自主只在 Data 和 Knowledge 内部

模型提议，代码决定。公司、文档范围、有效期和 SQL 校验不交给模型。同期数据也支持这一点：模型自己选 Data / Knowledge 只对 36～37 题（共 48 题），Planner 对 43 题，多出来的主要是多调了工具。

## D43 迷路退回固定路线，权限拒绝不退回

模型找不到路时，固定路线还能给出答案。权限拒绝是明确的结论，换条路再试等于绕过。

## D44 熔断只统计基础设施故障

模型写错 SQL 不算服务坏了。如果计入熔断，一个写错 SQL 的模型会让所有公司都查不了数据。

## D45 不开放 `template_query`

它连的是默认业务库，不是公司数据源，有跨公司风险，线上也没有接入。

## D46 工具模式默认关闭，切换由用户决定

同期数据显示准确率没有变差，但费用是固定路线的约 1.7～1.8 倍，也没有在真实主链上跑过。数据还不足以说明应该切换。
