# 03 教学文档：从这个项目学 Agent 工程

读法：每课先看“一句话”，再对着代码看“调用链”，最后做“自测题”（答案在文末）。
每课都对应真实提交，可以用 `git show <提交号>` 看改动。

---

## 第 1 课 系统全貌：一个问题怎么变成报告

**一句话**：API 只负责“收下并记账”，真正的分析在 Worker 里异步完成，最后由代码规则决定能否发布。

**调用链**
1. `conversations/api.py` 收到消息 → `conversations/service.py` 在**同一个数据库事务**里写入任务和 Outbox 事件。
2. API 立刻尝试投递；即使失败，`beat` 每 5 秒运行 `publish_pending_analysis_task_events` 补投。
3. Worker 的 `process_analysis_task` 先 `claim_execution`（原子更新 queued→running，拿到租约），再从数据库恢复冻结的公司、数据源、文档范围。
4. `run_analysis` 跑 LangGraph：Planner → 计划语义复核 → Data/Knowledge → Reviewer → 确定性路由器（决定重试或结束）。
5. `_save_workflow_result`：`validate_report` + `decide_completion` 决定 completed / awaiting_review / needs_clarification / failed。

**为什么这样设计**：HTTP 请求不能等几十秒的模型调用；把“接单”和“干活”分开，API 崩了任务也不丢，Worker 崩了能按检查点续跑。

## 第 2 课 可观测性：日志、追踪、指标

**术语**
- **日志（log）**：一条条事件，如“节点完成”“调用失败”。
- **追踪（trace）**：把同一个任务的所有事件按时间串起来。
- **指标（metric）**：聚合后的数字，如 p95 耗时、成功率。

**本项目做法**（提交 181b7d2、4997162）
- 每条日志自动带 `request_id`、`task_id`、`execution_attempt_id`、`component`。实现：`ContextVar`——在任务入口 `set` 一次，同一执行上下文里任何地方打的日志都能读到，结束时 `reset`。
- 脱敏放在唯一出口 `JsonFormatter.format`，调用 `redact_text` 逐段替换。
- Celery Worker 默认会接管日志；必须连接 `setup_logging` 信号，才会用项目自己的格式化器。

**你要带走的经验**：测试通过 ≠ 系统在用。部署后在真实容器里写一条“探针日志”看输出，是最便宜的系统级验证。

## 第 3 课 可靠投递：Outbox、至少一次、幂等、竞态

**术语**
- **Outbox（发件箱）**：把“要发的消息”和业务数据写在同一事务里，之后由发布器负责真正发出，避免“数据写了消息没发”。
- **至少一次投递**：消息可能重复到达；所以接收方必须**幂等**（同一消息处理多次结果不变）。
- **竞态（race condition）**：两个进程执行顺序和预期不同导致结果出错。
- **租约（lease）**：一段时间内的独占权；过期后别人可以接手。

**真实案例**（提交 ce8912f）
- 正常顺序：API 发消息 → API 记 `broker_accepted` → Worker 认领 → 记 `worker_claimed`。
- 出错顺序：API 发消息 → **Worker 已认领**（此时事件还是 publishing，更新落空）→ API 才记 `broker_accepted` → 事件再也没人推进 → 每 120 秒租约到期被重发，事件 163 被重发 1634 次。
- 证据：卡住事件的认领延迟 1.3–1.8s（正常 32ms）；三个任务的 Worker 认领都比 API 完成早 26–29ms；数据库日志无死锁（否定了另一个假设）。
- 修复：认领成功就推进事件（不管它当时处于哪个未认领状态）；重投递遇到已终态任务时关闭残留事件。

**排错方法论**：先列出所有假设 → 找能**否定**假设的证据（死锁日志）→ 用时间线数据证实剩下的假设 → 写出能复现的失败测试 → 再修。

## 第 4 课 评测：怎么知道“改好了”

**组件评测 vs 端到端评测**：端到端只告诉你“整体对不对”；组件评测告诉你“哪一环变了”。改 RAG 后端到端成功率不变，但召回率下降，说明下游在替上游兜底，迟早会出问题。

**检索指标**（`app/modules/evaluation/retrieval.py`）
- **Hit@k**：前 k 个结果里至少有一篇相关文档的问题比例。
- **Recall@k**：前 k 个结果找回了多少比例的相关文档（一个问题有 3 篇相关文档，找回 2 篇就是 0.67）。
- **MRR**：第一个相关结果排名的倒数的平均值（排第 1 得 1，排第 2 得 0.5）；衡量“好结果是否排在前面”。
- 同一文档的多个 chunk 只算一次，否则一篇文档能刷满前 k 名。

**拦截率与误拦率**（`app/modules/evaluation/report_gate.py`）
- 只测“坏样本被拦”是不够的，还要测“好样本不被拦”。
- 每个坏样本只破坏一条规则，并核对拦截原因——否则会出现“因为样本本身写错而被拦”的假阳性。本次首版就踩了这个坑。

**录制回放**（`app/core/gateway/replay.py`）
- 录一次真实模型输出，按请求哈希保存；之后回放免费、结果可复现。
- 回放缺失时直接报错，绝不偷偷调用付费模型。
- 适合：改 SQL 校验器、报告规则等下游代码后复测。不适合：比较提示词（提示词一改就是新请求）。

## 第 5 课 读懂一份检索基线

本项目真实数据（19 个问题，153 篇文档）：

| 策略 | 最终 Hit@3 | MRR | 耗时 |
|---|---|---|---|
| 向量 + 重排 | 0.789 | 0.789 | 67s |
| 只用向量 | 0.789 | 0.789 | 0.6s |
| 双切块 + 重排 | 0.632 | 0.632 | 57s |

**怎么读**
1. 先看样本量：19 题里一题就是约 5 个百分点，差 1 题不算显著。
2. 重排和不重排数字相同，但没命中的题不同——说明重排在“换题对错”，不是净提升。要扩样才能下结论。
3. 双切块明显变差，不是“切块越多越好”。读代码找到原因：合并后排序丢了关键词重叠加权。**指标告诉你哪里不对，代码告诉你为什么。**
4. 候选 Recall@10 只有 0.789：有两成问题连前 10 都没找回相关文档，后面重排再好也救不回来。这就是为什么下一步要做“关键词召回 + 向量召回”两路合并（RRF）。

**RRF（倒数排名融合）一句话**：每一路结果按排名给分 `1/(60+排名)`，把各路得分相加再排序；不需要把不同来源的分数调到同一尺度。

## 第 6 课 并发与可靠性：用测试证明“只有一个人干活”

**本项目真实案例**（提交 6e3452a）：4 个线程同时认领同一任务。认领本身是安全的（原子 UPDATE 只有一个成功），但被拒的 3 个线程同时写“认领被拒”审计事件，序号都算成同一个值，撞唯一约束，Worker 抛异常。

**你要带走的经验**
- 并发问题单线程测试永远测不出来；要用真实数据库、多个连接、`Barrier` 让线程同时起跑。
- 修复前先确认“去掉修复必失败、加上修复必通过”，各跑多次——否则可能只是碰巧通过。
- 修并发 bug 时要想清楚锁会不会挡住别的关键路径（本例中行锁会挡住心跳，所以选了保存点重试）。

**围栏令牌（fencing token）**：每次认领生成一个新的执行编号；写结果时带上“只有当前编号还是我才写”的条件。旧 Worker 即使醒过来，也因为编号不匹配而写不进去。

**重试三分类**：可重试（超时、连接断、限流）、不可重试（参数错、权限不足、文件不存在）、需人工。把永久错误当成可重试，只会让失败来得更慢。

## 第 7 课 付费评测的正确姿势

**本项目真实流程**（2.5.5）
1. 先用免费模拟模型空跑，确认脚本本身没错（39 次调用都发生了、计数正确）。
2. 核对“实际用的模型”和“价格表里的模型”一致，否则费用预估没有意义。
3. 设两道硬上限：调用次数和预估费用；每次调用前按最坏情况预留，超了就不调用。
4. 录制：40 次调用，约 $0.024。
5. 回放：0 次调用，结果逐条一致——以后改下游代码可以免费复测。

**读 64% 准确率时要问的三个问题**
- 错的是模型，还是标签？（本次 5 个题本来是测故障恢复的，不是测路由的。）
- 有没有两种答案都合理？（“某新产品”被要求澄清，并不算错。）
- 剩下的才是真问题（3 个），交给提示词工程去改，并用同一份评测验证。

## 第 8 课 标签本身也需要设计

同一份录音，换一套标签，准确率从 64.1% 变成 88.2%。这说明**评测结论一半取决于标签**。

**本项目的做法**
1. 先写规则（R/A/E 编号），再逐题套用；每个放宽都要写规则编号。
2. 原标签永远保留在首位，不删除、不覆盖。
3. 一致性复查：同一规则要套到所有符合条件的题上，包括模型本来答对的题——否则就是“只给模型错的题开后门”。
4. 状态标“待确认”，由没参与标注的人审阅。

**最严格的做法（生产团队常用）**：两个人在看模型输出之前独立标注，计算一致率（如 Cohen's kappa）；一致率低的题说明题目本身有歧义，需要改题而不是改标签。

## 第 9 课 故障演练：在真实系统上验证“会恢复”

**本项目真实结果**（9 个任务，最坏 $0.031）

| 故障 | 系统怎么扛住的 |
|---|---|
| 杀掉 Worker | 租约 120 秒过期 → 恢复任务把它转 retrying → 新执行接管；被打断的模型调用记为“费用未知”，而不是当作 0 |
| Redis 停了还在提交 | Outbox 让任务先入库；Redis 恢复后发布器 19 秒内补投 |
| 运行中 Redis 断开 | 模型调用和数据库写入不经过 Redis，任务照常完成 |
| 超时 | 可重试 → 带抖动重试 → 单任务预算耗尽后截停，不会无限重试 |
| 两个 Worker + 重复投递 | 原子认领 + 围栏，只有 1 个执行；3.2 修好的审计序号竞态没有复发 |
| 运行中取消 | 围栏条件要求 status=running，迟到结果写不进去 |
| **数据库重启** | **没扛住**：任务直接失败、不重试——演练的价值就在于发现这种问题 |

**你要带走的经验**
1. 演练前写好“期望行为”和“停止条件”，演练后对照填“实际行为”。
2. 演练会暴露你没想到的设计细节：超时在受理时冻结，所以只改 Worker 无效。
3. 演练只负责发现问题；修复另开工单，先写复现测试。
4. 结束后一定要核对环境恢复：服务数、Worker 数、配置值、无遗留任务。

## 第 10 课 修复要用复测来验收

**本项目真实经过**（3.6）
1. 第一次修复：让 Planner 遇到数据库断连时向上抛。单元测试全绿。
2. 复测 4b：通过——但重启时任务恰好没碰数据库，**通过不等于修好了**。
3. 改成“停库 8 秒”复测 4c：日志仍显示被吞掉。原因：实际被捕获的是第二个异常 PendingRollbackError，第一个异常藏在 `__context__` 里。
4. 第二次修复：沿异常链判断根因；补“真实异常链”的测试；复测 4d 通过。

**你要带走的经验**
- 测试要用“真实发生过的异常形状”，而不是你以为会发生的形状——把日志里的异常链抄进测试。
- 演练要能稳定触发故障路径；碰运气通过的演练没有证明力。
- 系统要有多层兜底：重试分类是第一层，执行租约恢复是最后一层。

## 第 11 课 纵深防御：每一层都要能单独挡住攻击

**本项目 SQL 五层**：契约（只允许单条 SELECT）→ AST（语法树检查）→ 范围（行级安全）→ 执行（只读账号、只读事务、超时、行数上限）→ 审计。

**真实发现**：AST 层原来只检查“最外层是不是 SELECT”和“表在不在白名单”，于是 `WITH d AS (DELETE ...) SELECT * FROM d` 能通过——最外层确实是 SELECT。幸好执行层的只读账号和只读事务挡住了。

**你要带走的经验**
1. 检查要遍历整棵语法树，不能只看根节点。
2. 测“拦截”时要确认是被**目标规则**拦下的：第一次探测用了不存在的表名，全被表检查拦住，看上去很安全，其实什么都没测到。
3. 收紧规则前先准备“好样本”（历史真实 SQL），防止误拦正常业务。
4. 为什么不能靠提示词约束模型：提示词是建议，模型可能被用户问题里的注入内容诱导；只有代码和数据库权限是强制的。

5. 测某一层时要把前面的层关掉：4.4 的执行层测试把 AST 校验换成空函数，攻击才真正到达数据库。否则“通过”只说明 AST 拦住了，执行层没被测。
6. 4.4 发现另一条路径（模板查询）没有只读事务，只靠账号权限这一层，已补上（4.4.1）。
7. 一个真实的错误：我曾报告这条路径“用超级用户连接”，依据是自己用 `psql -U business_app` 登录后查到的角色——那是**我登录用的账号**，不是程序用的账号。从真实代码路径查询后才发现实际是 `business_readonly`。安全结论必须从被测路径本身取证，不能从旁路推断。

**补充：SQL 结果评测（2.5.6）教会我们的**

1. 拒绝回答也有代价。19 题里没有放行一个错误数字，看似很安全；但 4 条正确的 SQL 被拦下，用户只会看到“答不了”。安全和可用要分开衡量。
2. 通过率要拆开看。同样是“未通过”，“模型写错了”要改提示词，“写对了被拦”要改校验或补指标登记，修法完全不同。
3. 测试数据决定能发现什么错误。演示数据的订单状态全是 delivered，所以漏写状态筛选的 SQL 结果也对，这类错误测不出来。

**补充：修过度拦截（5.0）教会我们的**

1. 放宽规则之后要重新看安全指标。这次通过率上升的同时，就出现了把“无数据”报成 0 的错误，是评测抓到的。
2. 单次通过率会骗人。模型每次回答都可能不同，要多跑几次才能判断提升是不是真的。
3. 留出题看过就不再独立。依据某题的结果改系统后，这题的分数不再能代表新问题上的表现。

**补充：P0 基线教会我们的**

1. 小样本结论会反转。19 题时重排看起来没用，64 题时明显有用。幸好当时没有直接删掉。
2. 要分开看召回和排序。25% 的问题在召回阶段就丢了，重排再好也救不回来，这决定了 P1 要先补关键词召回。
3. 能取到数据不等于用对了数据。陷阱题里答案都被取到了，但旧版本也都在，10 题还排在新版本前面。

21. 为什么 COALESCE(SUM(x), 0) 要被拒绝，COUNT 返回 0 却没问题？
22. 陷阱题“找到答案”是 12/12，为什么这部分还是不合格？

### 参考答案
1. 模型调用耗时长且可能失败；同步执行会占满 Web 进程、超时丢任务，也无法重试和续跑。
2. 不复原的话，同一线程处理下一个任务时会带着上一个任务的编号，日志会串号。
3. 网络和进程随时可能失败，“恰好一次”在分布式系统里代价极高；允许重复、让接收方幂等，简单且可验证。
4. 等待会拖慢所有任务，还要设计等待超时；而“认领成功”本身就是送达证据，直接用它推进状态更简单、没有新的等待点。
5. Hit@3 = 1（有相关文档）；Recall@3 = 1/2 = 0.5（只找回 A，同一文档的两个 chunk 算一次）；MRR = 1/2 = 0.5（第一个相关结果排第 2）。
6. 只测坏样本，系统“全部拒绝”也能得满分；误拦率才能发现规则过严，比如合法的四舍五入被拦。
7. 自动补录会让“免费评测”在提示词变化后悄悄产生费用，违反先申请再批量调用模型的规则；显式报错让花钱成为一个有意识的决定。
8. 还不能。19 题样本里两者没命中的题不同，说明重排有作用但不是净提升；而且没看“回答质量”和“证据不足拒答率”。应先扩充评测集，再单独比较这一个变量。
9. Worker 可能在追加事件后、提交前做几十秒的模型调用，行锁会一直被持有，心跳线程更新同一行被阻塞，租约过期后任务被别人接管——会把一个小问题变成重复执行的大问题。
10. 很多任务同时失败（例如一起被限流）时，固定等待会让它们同一时刻重试、再一起失败；抖动把重试时间打散。
11. 项目的预算只在任务上下文里生效；评测脚本直接调模型时没有任务，预算不会拦截，必须自带闸门。
12. 那等于“为了通过而改期望值”。正确做法是保留原始基线，单独记录争议，由人决定是否建立新的标签集，并且新标签集要在看模型答案之前定好。
13. 如果只给模型答错的题放宽，就是按结果挑规则；规则必须与模型输出无关、对所有符合条件的题一视同仁，结果才可信。
14. 超时在 API 受理任务时冻结进任务快照，只改 Worker 不影响已受理的任务。好处是运行中的任务规则不会被中途改变，结果可复现、费用可预期。
15. 它只表示“之前的数据库错误没回滚”，原因可能是连接中断，也可能是唯一约束等永久错误；直接放宽会让永久错误也被重试。要先区分原因、写复现测试再改。
16. 重启只用几秒，任务在那段时间里恰好没有访问数据库，故障路径根本没被触发；要用“停库 8 秒”这种能稳定触发的方式。
17. 纵深防御要求每层独立成立：数据库权限可能被误配（比如换成 owner 账号连接），那时 AST 层就是唯一的防线；而且 AST 规则在代码里，可以测试和审查。
18. 不关掉的话攻击先被 AST 拦下，测试通过也证明不了执行层；关掉才能证明它单独成立。跳过是为了让没有演示库的开发机也能跑测试集；风险是 CI 里忘了注入变量时这 26 项会静默不跑，所以要在 CI 里显式提供并检查“跳过数”。
19. 账号权限可能被误配，只读事务是独立的一层，而且只改两行、没有额外代价。如果只断言“有报错”，修复前账号权限就会报错，测试同样通过，证明不了只读事务生效；指定错误类型才能确认是这一层拦下的。
20. 因为 4 条正确的 SQL 被拦了，用户拿不到本该能给的答案；而且数据里没有覆盖某些错误类型，“没发现错误”不等于“没有错误”。先提交答案，是为了让 git 历史证明答案不是照着模型输出写的。
21. SUM 没有数据时返回空，改成 0 就把“查不到”变成了“金额为 0”，会误导决策；COUNT 没有数据时返回 0，这本身就是真实结果。
22. 因为旧版本同样进了前 3，10 题还排在新版本前面。模型可能引用旧规定，所以要在检索时就排除不适用的版本。
