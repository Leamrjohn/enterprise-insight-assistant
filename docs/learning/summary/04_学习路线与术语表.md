# 04 学习路线与术语表

## 建议的学习顺序

建议按下面的顺序学，每一步都跟一个真实发生过的问题对应。先看问题，再看代码，记得更牢。

| 顺序 | 主题 | 从哪个真实问题入手 | 要读的代码 | 自测题（在 [03_teaching_guide.md](../03_teaching_guide.md)） |
|---|---|---|---|---|
| 1 | 任务为什么要异步 | API 不能在请求里跑几十秒的模型 | `backend/app/modules/workflow/tasks.py` | 第 1 题 |
| 2 | 至少一次投递和幂等 | 事件被重复发布 1634 次 | `workflow/delivery/outbox.py` | 第 3、4 题 |
| 3 | 并发和竞态 | 4 个 Worker 抢同一个任务 | `workflow/audit/events.py` | 第 9 题 |
| 4 | 重试和错误分类 | 数据库中断导致永久失败 | `backend/app/db/errors.py` | 第 10、15、16 题 |
| 5 | 纵深防御 | CTE 里藏的 `DELETE` | `analysis/data/sql_validator.py`、`sql_executor.py` | 第 17、18、19 题 |
| 6 | 确定性校验和模型的分工 | `COALESCE` 把无数据变成 0 | `analysis/metrics/metric_validation.py` | 第 21 题 |
| 7 | 评测方法 | 为什么 100% 拦截不可信 | `modules/evaluation/report_gate.py`、`sql_results.py` | 第 6、12、13、20 题 |
| 8 | 成本控制 | 评测脚本绕过了项目预算 | `scripts/evaluation/run_planner_route_evaluation.py` | 第 7、11 题 |

## 建议的动手练习

这些练习都不花钱。做完后用 `git checkout -- <文件>` 撤销修改（只对你自己刚改的文件这样做）。

1. **看测试怎么保护代码：** 把 `sql_validator.py` 里调用 `_validate_no_side_effects` 的那一行注释掉，运行 `test_sql_adversarial.py`，看有多少攻击重新通过。
2. **感受抖动：** 在 Python 里多次调用 `_retry_countdown(2)`，观察等待时间的变化。
3. **看校验如何判断：** 用 `assess_metric_query` 分别测试 `SUM(o.total_amount)` 和 `COALESCE(SUM(o.total_amount), 0)`，比较返回的 `status`。
4. **读一条真实录制：** 打开 `artifacts/evaluation-20261102-sql-results-v4/cassettes/` 里的文件，看模型实际返回了什么。
5. **审核标准答案：** 阅读 [sql_results_v1.json](../../../backend/tests/fixtures/evaluation_sql/sql_results_v1.json)，判断每题的口径你是否同意。这既是学习，也是目前最需要你做的事。

## 贯穿始终的 8 条经验

1. **先复现，再修改，再验证。** 3.6 的第一次修复就是靠复测才发现没修到根上。
2. **测试通过不等于系统正常。** 2.3 的测试全部通过，部署后才发现 Worker 没用这套日志。
3. **确认是被目标规则拦下的。** 错的样例也可能带来“100% 拦截”的好成绩。
4. **不为了通过而改期望值。** 有争议的标签另建一份，原基线保留。
5. **从被测路径本身取证。** “超级用户”的错误结论，就是从旁边的现象推断出来的。
6. **能用代码判断的，不交给模型。** 模型负责理解含义，能否放行由确定性代码决定。
7. **拒绝也有代价。** 安全和可用要分开衡量。
8. **小样本和单次结果要谨慎对待。** 模型有随机性，看过的留出题也不再独立。

## 术语表

### 任务和可靠性

| 术语 | 一句话解释 |
|---|---|
| Worker | 在后台执行任务的进程 |
| Celery | 本项目用的后台任务框架 |
| Redis | 本项目用作消息队列的内存数据库 |
| Outbox | 把事件和业务数据写进同一个事务，再由发布器发送，避免“存了但没发” |
| 至少一次投递 | 消息可能重复，但不会丢 |
| 幂等 | 同一个操作做多次，效果和做一次相同 |
| 竞态 | 结果取决于两个进程谁先完成 |
| 租约 | 带过期时间的占用权，持有者崩溃后别人可以接管 |
| 心跳 | Worker 定期更新状态，表明自己还活着 |
| 围栏（fencing） | 用执行编号确保过期的执行不能写结果 |
| 事务 | 一组数据库操作，要么全部成功，要么全部撤销 |
| 保存点（savepoint） | 事务里的中间点，可以只撤销到这里 |
| 行锁 | 锁住一行数据，别人要等释放后才能修改 |
| 抖动（jitter） | 给等待时间加随机数，避免大家同时重试 |
| 异常链 | 一个错误引发另一个错误时，Python 保留的前后关系 |
| ContextVar | 上下文变量，这里用来让日志自动带上任务编号 |
| 脱敏 | 把密钥、手机号等替换成 `[REDACTED]` |
| 故障演练 | 主动制造故障，确认系统真的能恢复 |

### SQL 和安全

| 术语 | 一句话解释 |
|---|---|
| AST（语法树） | 把 SQL 解析成树形结构，便于程序检查 |
| CTE | SQL 里 `WITH x AS (...)` 这种临时命名的子查询 |
| 只读事务 | 这次数据库操作只能读，不能改 |
| `statement_timeout` | 单条 SQL 的最长运行时间 |
| 超级用户 | 权限最高的数据库账号，可以绕过所有权限检查 |
| 行级安全（RLS） | 数据库按行限制谁能看到什么数据 |
| 纵深防御 | 设置多层防护，一层失效还有下一层 |
| 黑名单 / 白名单 | 只禁止列出的内容 / 只允许列出的内容 |
| 对抗测试 | 故意模拟攻击来测试防护 |
| `COALESCE` | 取第一个非空值，常用来把空值改写成 0 |

### Agent 和评测

| 术语 | 一句话解释 |
|---|---|
| Planner | 判断问题该怎么处理的规划模块 |
| Data Agent | 写 SQL 并查询经营数据的模块 |
| Reviewer | 检查报告的模块 |
| 语义审查 | 让第二个模型检查 SQL 的含义对不对 |
| 确定性校验 | 用代码规则判断，同样的输入永远得到同样的结果 |
| 指标契约 | SQL 必须声明用哪个已登记指标，并符合它的公式和条件 |
| 过度拦截 | 正确的内容被错误地拒绝 |
| 组件评测 | 单独评测一个环节，而不是跑完整流程 |
| 冒烟测试 | 用少量固定问题快速检查系统是否基本正常 |
| 录制回放 | 第一次保存模型回复，以后直接读取，不花钱 |
| 标准答案（gold） | 人工确认的正确答案，用来给模型打分 |
| 开发集 / 留出集 | 用来调优的题 / 专门留着检验、不用来调优的题 |
| 结果指纹 | 用查询结果算出的校验值，用来比对结果是否相同 |
| RAG | 先检索相关文档，再让模型基于文档回答 |
| Hit@3 | 前 3 个检索结果里有相关文档的题目比例 |
| Recall@3 | 相关文档中被找回到前 3 名的比例 |
| MRR | 第一个相关结果排名越靠前，分数越高 |
| 重排 | 用第二个模型把检索结果重新排序 |
| 影子实验 | 只记录模型会怎么做，不真正执行 |
