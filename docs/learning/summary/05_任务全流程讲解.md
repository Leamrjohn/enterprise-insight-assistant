# 05 任务全流程讲解

本文按当前代码（提交 `d1aa730`）和真实任务 315 的记录，讲一个任务从提问到发布的完整过程，以及和修改前的区别。

示例任务是 **“2025年8月已交付订单的毛利是多少？”**。它耗时 14.7 秒，调用模型 5 次，花费 $0.00345，得到的毛利 2259844.98 与标准答案一致。

**总的进步：** 主流程的结构没变，这次也没有改数据库结构。进步在于主流程的几个关键环节修好了，安全防线补上了，还多了能发现问题的测试和评测。

## 总览

```text
用户提问
  ↓
① API 受理：检查权限，把任务和待发事件存进同一个事务
  ↓
② 投递：发布器把事件发到 Redis 队列（消息队列）
  ↓
③ Worker 认领：拿到任务的占用权（租约），每 40 秒续一次
  ↓
④ 准备上下文：对话历史、记忆、文档范围、工具运行层
  ↓
⑤ Planner 规划 → 语义复核计划
  ↓
⑥ 按路线取证据
   ├ 数据：写 SQL → 审查 → 指标校验 → 语法树检查 → 只读执行
   └ 知识：向量检索 → 排序 → 重排
  ↓
⑦ Reviewer：用代码生成报告，校验数字和引用，模型复核证据
  ↓
⑧ 路由器：用代码决定结束、重试还是重新规划
  ↓
⑨ 确定性校验 + 发布决定 → 保存结果
```

任务 315 的真实事件记录（节选，保存在 `workflow_events` 表）：

```text
execution_claimed                       Worker 认领
context_selected                        选好上下文
planner_node 开始 → 完成                 规划
planner_semantic_review_node 开始 → 完成  复核计划
data_node 开始
  sql_query 开始 → 完成（16 毫秒）         执行 SQL
data_node 完成
reviewer_node 开始 → 完成                生成并检查报告
smart_router_node 开始 → 完成            决定下一步
execution_finished                      保存结果
```

## 每一步的细节

### ① API 受理

你发消息后，接口是 `POST /conversations/{id}/messages`。

系统会依次做这些事：

- 检查你有没有分析权限，文档是否在你可见的范围内。
- 检查公司的数据源和表结构快照是否就绪，没就绪返回 409。
- 检查任务数量和系统容量，超限返回 429 或 503。
- 冻结这个任务的规则：超时、模型预算、工具策略、对话上下文。之后改配置，也不影响已受理的任务。
- **把任务和 Outbox 事件（待发送的消息）写进同一个事务。** 要么都存下，要么都不存，不会出现“任务存了，消息没发”。

然后接口立刻返回 `queued`，不会让你一直等着模型跑完。

**进步：** 受理逻辑基本没变。发消息的慢请求（p90 约 1.35 秒）是这次才查出来的，原因还没查。

代码：[conversations/api.py](../../../backend/app/modules/conversations/api.py)、[conversations/service.py](../../../backend/app/modules/conversations/service.py)

### ② 投递

API 提交后马上发布一次事件。即使 Redis 挂了也不会丢，定时任务每 5 秒会补发一次。演练中，Redis 恢复 19 秒后任务就完成了。

**进步：** 修好了事件卡住的问题。

| | 修改前 | 现在 |
|---|---|---|
| Worker 比 API 记录状态更快时 | 事件卡在 `broker_accepted`（队列已接收），有一条被重复发布了 1634 次 | 认领成功就推进状态，不管谁先谁后 |
| 重复投递遇到已结束的任务 | 事件一直残留 | 自动关闭 |

代码：[delivery/outbox.py](../../../backend/app/modules/workflow/delivery/outbox.py)

### ③ Worker 认领

Worker 用 `_claim_task` 认领任务，创建一条执行记录，拿到 120 秒的租约，并每 40 秒续一次（心跳）。如果 Worker 崩溃，定时任务每 10 秒检查一次过期的租约，把任务交给新的执行。

**进步：**

- **并发：** 以前多个 Worker 抢同一个任务时，落败的一方会抛异常。现在在保存点（事务里的中间点）里重试事件序号，只有一个成功，其余正常退出。
- **日志：** 以前 Worker 日志不走项目格式，也不脱敏。现在每行都带任务编号，密钥、手机号都会替换成 `[REDACTED]`。

代码：[workflow/tasks.py](../../../backend/app/modules/workflow/tasks.py)、[lifecycle/execution.py](../../../backend/app/modules/workflow/lifecycle/execution.py)、[audit/events.py](../../../backend/app/modules/workflow/audit/events.py)

### ④ 准备上下文

Worker 会读取受理时冻结的对话上下文，再取记忆（最多 8 条）和文档、附件范围，并创建 `ToolRuntime`（工具运行层，所有工具调用都经过它）。这些选择记录在 `context_selected` 事件里。

**进步：** 这部分没有改动。记忆和上下文的选择策略还比较简单，要到阶段 7 才处理。

### ⑤ Planner 规划

Planner 用模型判断问题的路线：只查数据、只查文档、两者都查、需要澄清，或直接回复。之后由语义复核再检查一次计划。任务 315 走的是“只查数据”。

如果问题缺信息，流程到这里就结束了，比如任务 316（“不存在的测试区域”）就被要求补充区域。

**进步：**

- **路由有了成绩单：** 原标签准确率 64.1%，路由专用标签 88.2%。路由逻辑本身没改，仍错的 4 题留给阶段 7.5。
- **基础设施错误不再被吞掉：** 以前数据库中断时，Planner 把错误当成业务失败，任务直接永久失败。现在错误会向上抛给 Worker，按可重试处理。

代码：[planner_agent.py](../../../backend/app/modules/analysis/planner/planner_agent.py)、[db/errors.py](../../../backend/app/db/errors.py)

### ⑥ 取证据：数据路径

**这一步改动最大。** 一条 SQL 要过这些关卡：

| 关卡 | 做什么 | 这次的变化 |
|---|---|---|
| 1. 模型写 SQL | 生成 SQL 和查询契约（声明用哪个指标） | 不再示范 `COUNT(*)`，禁止借用不相符的指标 |
| 2. 语义审查（模型） | 判断 SQL 是否真正回答了问题 | **以前看不到指标定义，现在能看到** |
| 3. 指标校验（代码） | 核对公式、强制条件、时间列 | 指标从 2 个增加到 6 个；毛利校验公式；**拒绝 `COALESCE` 把无数据改写成 0** |
| 4. 工具运行层（代码） | 重新检查授权、预算，由服务端设定超时，记录审计 | 被拒绝时会说明该怎么改 |
| 5. 语法树检查（代码） | 只允许单条 SELECT，限定表范围 | **能查出藏在内部的写入、行锁和危险函数：54 种攻击从拦 27 种变成全拦** |
| 6. 只读执行（数据库） | 只读账号、只读事务、超时、行数上限 | 有了 29 项自动测试；模板查询也补上了只读事务 |

第 1～3 关不通过时，部分情况可以修正一次（最多尝试 2 次）。任务 315 的 SQL 一次通过，执行只用了 16 毫秒。

代码：[data_agent.py](../../../backend/app/modules/analysis/data/data_agent.py)、[metric_validation.py](../../../backend/app/modules/analysis/metrics/metric_validation.py)、[tool_runtime.py](../../../backend/app/modules/runtime/tool_runtime.py)、[sql_validator.py](../../../backend/app/modules/analysis/data/sql_validator.py)、[sql_executor.py](../../../backend/app/modules/analysis/data/sql_executor.py)

### ⑥ 取证据：知识路径

问题需要查文档时，走向量检索前 10 条，排序后再重排取前 3 条。任务 315 没有走这条路径。

**进步：** 这部分代码没改，但有了基线：Hit@3（前 3 条结果里有相关文档的题目比例）为 0.789。也发现重排在这 19 题上没有提升，却慢约 110 倍，这个问题留到阶段 6 再验证。

### ⑦ Reviewer 检查

一个容易误解的地方：**任务 315 的报告不是模型写的。** `compose_report` 用代码把证据组成报告，所以才有“毛利为2259844.98”这样的句子。这样模型没有机会在报告里编数字。

然后系统校验数字和引用，再让模型判断证据是否足够回答问题。模型只能把结论往保守的方向改（比如改成 `partial`），不能批准发布。

**进步：** 代码没改，但现在有评测证明校验有效：15 种篡改全部拦截，4 个合法样本 0 误拦。

代码：[reviewer_agent.py](../../../backend/app/modules/reporting/reviewer_agent.py)

### ⑧ 路由器决定下一步

`choose_next_action` 完全用代码决定结束、重试还是重新规划，不询问模型。图最多运行 20 步，防止死循环。

**进步：** 新增了回归测试，确认死循环会被截断，并且不会再重试。

代码：[orchestration/router.py](../../../backend/app/modules/workflow/orchestration/router.py)、[orchestration/graph.py](../../../backend/app/modules/workflow/orchestration/graph.py)

### ⑨ 校验并发布

- `validate_report` 用代码校验报告结构和引用范围。
- `decide_completion` 决定最终状态：

| 情况 | 最终状态 |
|---|---|
| 报告校验通过 | `completed`，发布报告 |
| 证据不足 | `partial` |
| 含因果推测 | `awaiting_review`，等人工审批 |
| 缺信息 | `needs_clarification` |
| 流程失败 | `failed` |

写结果时还会确认“我还是当前的执行者”（围栏）。任务已被取消或被别人接管的话，旧执行就写不进去。演练验证过：运行中取消后，没有再调用模型，也没有产生报告。

代码：[reporting/validation.py](../../../backend/app/modules/reporting/validation.py)、[lifecycle/publication.py](../../../backend/app/modules/workflow/lifecycle/publication.py)

## 出问题时的区别

| 故障 | 修改前 | 现在 |
|---|---|---|
| 数据库中断几秒 | 任务永久失败 | 判为可重试。停库时连状态都写不进去，所以恢复后由租约接管完成 |
| 模型被限流 | 所有任务同时重试 | 等待时间乘 0.5～1.5 的随机系数，分散重试 |
| 权限错误、文件不存在 | 反复重试 | 不重试 |
| Worker 被杀 | 机制已有，没验证过 | 演练证实，约 2 分钟后接管完成 |
| Redis 中断 | 机制已有，没验证过 | 演练证实，任务不丢 |

## 还没有进步的地方

- **记忆和上下文：** 只是按时间选取，没有按相关性。
- **RAG：** 还没有关键词和向量的双路检索。
- **工具选择：** 由代码路由，模型不能自己选工具。
- **答不了的问题：** “未回款余额”这类没有登记的指标仍然答不了，这是你决定的取舍。
- **`partial` 状态：** 预算用完且没有报告时，任务仍标为 `partial`。

**证据的局限：**

- SQL 通过率只是一次录制的结果，模型有随机性。
- `COALESCE` 拦截没有在完整任务里验证过。
- 演示数据测不出漏写状态条件这类错误。
- SQL 标准答案还等你审核。
