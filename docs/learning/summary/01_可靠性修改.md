# 01 可靠性修改

**这部分回答的问题：** 进程崩溃、网络中断、数据库重启时，任务会不会丢失、重复或永远卡住？

Agent 系统比普通网站更需要关注这个问题，因为一次任务要调用多次模型，耗时长，也要花钱，中途出错的机会很多。

---

## 1. 日志脱敏和任务编号（2.3）

**为什么改：** 日志会被复制、转发、长期保存。修改前，密钥、邮箱、手机号都可能原样写进日志；排查一个任务时，也只能靠时间线人工拼接。

| | 修改前 | 修改后 |
|---|---|---|
| 敏感信息 | 消息和异常堆栈里原样输出 | 统一替换成 `[REDACTED]` |
| 按任务查日志 | 只有 `request_id` | 每行自动带 `task_id`、`execution_attempt_id` |
| Worker 日志 | 从未走项目格式，共享日志文件里 0 条 | 与 API 一样是脱敏的 JSON |

**关键修改**，让 Celery 使用项目的日志配置（[celery_app.py](../../../backend/app/core/celery_app.py)）：

```python
@setup_logging.connect
def _use_project_logging(**_kwargs) -> None:
    configure_logging(settings)
```

**意义：** 脱敏放在日志唯一的出口，以后写新代码不需要“记得脱敏”。

**一个重要的发现：** 离线测试全部通过，部署后才发现 Worker 根本没用这套配置。测试证明“函数是对的”，部署检查证明“系统真的在用这个函数”。

**还没解决：** uvicorn 访问日志还不是 JSON 格式；脱敏只覆盖已知格式，不能识别所有个人信息。

## 2. Outbox 事件卡住（Outbox 修复）

**先了解 Outbox：** API 把“任务”和“待发送的事件”写进同一个数据库事务，再由发布器发给队列。这样不会出现“任务存了，消息没发”。

**症状：** 12 条事件卡在 `broker_accepted`（队列已接收）状态，事件 163 被重复发布了 1634 次。

**根因：** 这是一个竞态（两个进程谁先完成，结果就不同）。正常顺序是 API 先记录“队列已接收”，Worker 再认领。API 请求慢时，Worker 比 API 早 26～29 毫秒认领，事件的状态就对不上了。

**排查过程值得一看：** 我先假设是“Worker 太快”或“数据库死锁”。Postgres 日志里 0 条死锁记录，排除了后者；再对齐任务 265、273、297 的时间线，证实了前者。

| | 修改前 | 修改后 |
|---|---|---|
| Worker 认领时 | 事件必须已是 `broker_accepted` | 任何未认领状态都能推进 |
| 重复投递遇到终态任务 | 事件一直留着，反复发布 | 关闭残留事件 |

```python
# 修改前
AnalysisTaskOutboxEvent.status == "broker_accepted"
# 修改后
AnalysisTaskOutboxEvent.status.in_(("pending", "publishing", "broker_accepted"))
```

**意义：** “Worker 成功认领”才是消息确实送达的可靠证据，不依赖两个进程谁先完成。

**结果：** 部署后约 90 秒，12 条事件自动恢复，发布器每轮发布 0 条。不需要手工改数据库。

**还没解决：** 没有用新任务真实触发过这个竞态，只有单元测试覆盖；API 为什么慢也还没查。

## 3. 多个 Worker 同时抢一个任务（3.2）

**症状：** 新增的并发测试首跑失败。4 个线程同时认领时，落败的 Worker 抛出异常，而不是正常返回“已被认领”。

**根因：** 审计事件的序号是“当前最大值 + 1”，同时计算就会撞上唯一约束。

| | 修改前 | 修改后 |
|---|---|---|
| 序号冲突 | 抛异常 | 在保存点里重试，最多 5 次 |

```python
for _ in range(_SEQUENCE_RETRIES):
    sequence = 当前最大序号 + 1
    try:
        with db.begin_nested():   # 保存点：失败时只回滚这一条
            db.add(event)
            db.flush()
        return event
    except IntegrityError:
        continue                  # 伪代码，真实代码见 audit/events.py
```

**为什么不用更简单的行锁：** Worker 可能在提交前调用模型几十秒。行锁会一直被占用，心跳更新不了同一行，租约就会过期，任务被别人接管。修一个小问题，反而引出重复执行的大问题（决策 D10）。

**意义：** 重复投递是正常现象，不应该引发异常。

## 4. 重试策略（3.3）

**为什么改：** 模型服务限流时，很多任务会同时失败。如果等待时间相同，它们会在同一秒重试，然后一起再次失败。权限错误这类永久错误，重试也没用，只是拖延失败。

| | 修改前 | 修改后 |
|---|---|---|
| 等待时间 | `2 ** (retries + 1)`，固定 | 乘上 0.5～1.5 的随机系数 |
| `PermissionError`、`FileNotFoundError` 等 | 反复重试 | 不重试 |

```python
def _retry_countdown(retries, *, random=None):
    base = 2 ** (retries + 1)
    return base * (0.5 + (random or _random.random)())
```

**意义：** 重试的目的是等问题消失。随机系数让重试时间分散，分类让系统不浪费时间在不会好的问题上。

## 5. 超时和步数上限（3.4）

这一项没有改应用代码，只新增测试，确认现有上限真的生效：路由死循环会被 20 步上限截断，Worker 遇到步数耗尽会进入 `failed`，不再重试。

**意义：** 兜底机制平时用不到，所以最容易在不知不觉中失效，需要测试来保护。

**有意没做：** 任务总时长上限（决策 D12）。现有的“步数 × 单步超时”已经间接限制了总时长。

## 6. 故障演练（3.5）

**为什么做：** 设计上说会恢复，不等于真的会恢复。所以我在真实运行的系统上制造了 8 种故障。

| 故障 | 结果 |
|---|---|
| 规划阶段杀掉 Worker | 约 2 分钟后新执行接管并完成 |
| Redis 停止时提交任务 | 任务入库，Redis 恢复 19 秒后完成 |
| 运行中停 Redis 30 秒 | 任务正常完成 |
| 运行中重启 PostgreSQL | **直接失败、不重试**（另立 3.6 修复） |
| 模型超时 | 重试，最后被模型预算截停 |
| 2 个 Worker + 重复投递 | 只有 1 个执行，无异常 |
| 运行中取消 | 取消后 0 次调用，没有报告 |

**学到的设计：** 第一次超时演练没生效，因为超时参数在任务受理时就写入了任务（决策 D18）。这样，运行中的任务规则不会被中途改变，结果和费用更可预期。

**观察到的问题（未修）：** 模型超时那个任务没有产生任何报告，状态却是 `partial`，容易误导。要不要改，涉及状态的定义，需要你决定。

完整结果见 [stage3_5_game_day_plan.md](../../design/stage3_5_game_day_plan.md)。

## 7. 数据库短暂中断（3.6）

**症状：** 数据库中断几秒，任务就永久失败。

**根因（修了两次才找到）：**

```text
数据库断开 → OperationalError（连接错误，应该重试）
     ↓ 网关在异常处理里用同一个坏连接记录调用
PendingRollbackError（看上去是另一种错误）
     ↓ Planner 的 except Exception 把它当成业务失败
任务 failed，不重试
```

第一次修复只判断了 `OperationalError`，但真正被捕获的是 `PendingRollbackError`，原始错误藏在它的 `__context__` 里。

| | 修改前 | 修改后 |
|---|---|---|
| 判断方式 | 只看最外层异常 | 沿异常链向上找根因（[errors.py](../../../backend/app/db/errors.py)） |
| Planner | 吞掉数据库错误 | 短暂数据库错误继续向上抛，交给 Worker |

```python
current = exc
for _ in range(_MAX_CHAIN_DEPTH):
    if current is None:
        return False
    if _is_connection_failure(current):
        return True
    current = current.__cause__ or current.__context__
```

**为什么不直接把 `PendingRollbackError` 设成可重试：** 它只表示“之前有错误没回滚”，原因也可能是唯一约束这类永久错误，重试不会好。

**实际恢复过程：** 停库 8 秒的复测中，错误被判为可重试。但停库时连“标记重试”都写不进数据库，最后是数据库恢复后由**租约恢复**接管完成的。所以租约机制不能删。

**意义：** 基础设施问题和业务问题要分开处理，业务代码不应该吞掉基础设施错误。

**还没解决：** Knowledge 工具遇到数据库错误时的分类，以及经营库中断时 SQL 工具的行为，都还没处理。
