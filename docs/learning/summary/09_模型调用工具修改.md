# 09 模型调用工具修改（P4，2026-11-02）

这份文档讲 P4 改了什么、数据怎么说、哪些没做到。数字都来自本次实际运行。

## 一句话结论

模型调用工具的版本已经写好，默认关闭，线上行为不变。准确率没有变差，但费用是固定路线的约 1.7～1.8 倍，也还没有在真实主链上跑过，所以数据还不足以支持切换。是否切换由用户决定。

## 什么是“模型调用工具”

- **固定路线：** 代码决定每一步，模型只负责写 SQL 或写回答。
- **模型调用工具：** 把工具清单给模型，由模型决定先看表结构、再查数据，看到错误原因后自己修改。

模型只能提议，代码决定是否执行。公司范围、文档范围、有效期、SQL 校验和权限都不交给模型。自主范围只在 Data 和 Knowledge 内部，Planner、Reviewer、确定性校验和发布都没变。

## 改了什么

1. **网关：** 支持原生工具调用，`deepseek-v4-flash` 实测可用。OpenAI 和本地网关没有实现，它们会拒绝，然后走固定路线。
2. **工具循环（`runtime/tool_loop.py`）：** 轮次、调用次数、修复次数、时长和“重复同一错误”的上限都由代码掌握。
3. **工具目录：** 每个工具写清做什么、何时用、何时不用、参数示例、常见错误，带版本号。
4. **Data 工具版：** `describe_table`、`run_sql`、`submit_result`、`report_insufficient`。结果只给模型前 5 行、总行数和统计，完整结果留在服务端。
5. **Knowledge 工具版：** 代码先搜一次，模型可以换词再搜，最多 3 次。公司、文档和有效期都由代码设置。
6. **失败处理（`runtime/tool_guard.py`）：**
   - 权限问题立即停止。
   - 参数或 SQL 错误把原因告诉模型。
   - 基础设施故障计入熔断器（连续失败太多就暂时不再调用，过一会儿放一个请求试探）。
   - 模型迷路时退回固定路线。权限拒绝不退回。
7. **灰度开关：** `model_tool_mode`（off / allowlist / all）和 `model_tool_company_ids`，默认 off。

## 顺手发现的真实问题

`RAGSearchInputSchema` 会丢掉 `validity_window`，所以线上检索一直按“今天有效”过滤。P1 的评测绕过了这一层，没有发现。也就是说，P1 说的“能回答过去某个时期的问题”，在这次修复前线上并不成立。这个修复对固定路线也生效，已部署。

## 没做到或要注意的

- **影子模式只是离线对比：** 没有在线上并行跑，因为并行会消耗任务预算。
- **任务预算可能不够：** 目前每节点最多 4 次模型调用，工具版在迷路时加上退回固定路线可能超过。这是根据轮次推算的，没有真实跑过。切换前要决定是否放宽。
- **故障演练的限制：**
  - 模型是脚本模拟的。
  - 熔断演练的故障是真实的连接被拒，但错误码由演练包装层赋予，没有经过 SQLTool 本身。
  - 只验证了 Data 带错误码停止，没有验证最终报告的 `partial` 状态。
  - 重排故障是模拟的。
- **`template_query` 没有开放：** 它连的是默认业务库，不是公司数据源，有跨公司风险。
- **评测题的来源：** P4 新增的故障题是我写的，等用户复核。选路提示词也只写了一版，没有调优。

## 学习笔记

- **症状 → 根因：** 线上查不到过去时期的文档 → 校验层的数据结构没有这个字段，悄悄丢掉了 → 评测直接调工具，绕过了校验层。教训是评测要走和线上相同的路径。
- **调用链：** `knowledge_node` → `ToolCallingKnowledgeAgent.run` → `run_tool_loop` → 模型提议 `search_documents` → 处理函数补上范围和有效期 → `GuardedTool` → `RAGTool`。
- **为什么这样设计：** 模型可以决定“下一步查什么”，不能决定“能查谁的数据”。后者错一次就是越权，必须由代码保证。
