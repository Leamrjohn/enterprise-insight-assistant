# 03 评测与过度拦截修复

**这部分回答的问题：** 怎么知道 Agent 答得对？改了代码之后，是变好了还是变差了？

**修改前：** 只能跑完整流程。每次都要花钱，结果受模型随机性影响，失败了也不知道是哪个环节的问题。

**修改后：** 每个环节可以单独评测（组件评测），能免费的就免费。

| 环节 | 评测方式 | 费用 | 第一次结果 |
|---|---|---|---|
| 检索 | 本地模型 | 免费 | Hit@3 0.789 |
| 报告校验 | 纯代码 | 免费 | 15 种篡改全部拦截，合法样本误拦 0/4 |
| Planner 路由 | 录制后回放 | 约 $0.024 | 原标签 64.1%；路由专用标签 88.2% |
| SQL 结果 | 录制后回放 | 约 $0.035 | 19 题通过 13 题 |

---

## 1. 录制回放（2.5.4）

**原理：** 第一次调用真实模型，并把回复存下来（录制）；以后同样的请求直接读取存好的回复（回放），不花钱。

**关键设计：回放时找不到录制就直接报错，不自动调用模型。** 否则提示词一改，“免费评测”就会悄悄变成付费运行（决策 D9）。

**费用闸门：** 评测脚本没有任务上下文，项目的预算治理不会生效。所以我加了 `BudgetGuardGateway`，调用前先估算最坏费用，超过上限就拒绝调用（决策 D14）。

代码见 [replay.py](../../../backend/app/core/gateway/replay.py)。

## 2. 检索评测（2.5.2）

| 策略 | Hit@3 | MRR | 耗时 |
|---|---|---|---|
| 段落 + 向量 + 重排（现行） | 0.789 | 0.789 | 67 秒 |
| 段落 + 向量，不重排 | 0.789 | 0.789 | 0.6 秒 |
| 段落 + 滑窗 + 重排 | 0.632 | 0.632 | 57 秒 |

**发现：** 在这 19 题上，重排（用第二个模型重新排序）没有带来提升，却慢了约 110 倍。

**为什么没有马上关掉重排：** 19 题样本太小，可能是假象。要先扩充评测集，再一次只改一个变量（决策 D13）。

## 3. 报告校验评测（2.5.3）

**测试方法：** 故意篡改合法报告（改数字、改引用等），看校验能不能拦住。

**一个常见陷阱：** 第一版显示 100% 拦截，但有的样例是因为缺字段才被拦，并不是被目标规则拦下。修改后，每种篡改都登记了预期原因，原因不符就不算拦截（决策 D8）。

**为什么要放合法样本：** 只测坏样本的话，系统“全部拒绝”也能得满分。

## 4. Planner 路由评测（2.5.5）

**结果：** 按原标签 64.1%。

**我没有直接改标签。** 改标签能让数字立刻变好看，但这正是“为了通过而改期望值”。14 道错题的人工归类是：

| 类型 | 题数 |
|---|---|
| 题目不适合做路由评测（如故障注入场景） | 5 |
| 两种决策都说得通 | 6 |
| 明确的 Planner 错误 | 3 |

之后按你确认的书面规则，另建了一份路由专用标签，得到 88.2%（34 题）。原标签和 64.1% 的基线都保留。仍错的 4 题留给阶段 7.5 的提示词工作。

**已知局限：** 写规则时我已看过模型输出，可能有偏向。

## 5. SQL 结果评测（2.5.6）

**为什么要自己写标准答案：** 夹具里的“80 条结果指纹”大多只是场景名称，真实校验值只覆盖 9 个问题，其中 6 个的答案还都是“查不到数据”。

**做法：**

1. 人工写 19 题的标准答案，其中 16 条是参考 SQL。
2. **先提交到 git，再调用模型**，这样可以证明答案不是看了输出才写的。
3. 运行真实的 DataAgent，比较查询结果的**数值**，不比较 SQL 写法（同一个问题有多种正确写法）。

**第一次结果：** 通过 13 题，放行的错误数字为 0。未通过的 6 题都是系统拒绝回答。

**把被拦的 SQL 再跑一遍后发现：**

| 题目 | SQL 是否正确 | 判断 |
|---|---|---|
| 华南区全年订单数、8 月毛利、各类费用、无订单客户数 | 正确 | 拦错了（过度拦截） |
| 未回款余额（没减已回款）、8 月收入目标（日期写法报错） | 错误 | 拦对了 |

**意义：** 同样是“未通过”，修法完全不同。只看通过率会把两者混在一起。

## 6. 修复过度拦截（5.0）

### 根因和修改

| 根因 | 修改前 | 修改后 |
|---|---|---|
| 登记的指标太少 | 只有销售额、客诉数量 | 新增已交付订单数、毛利、费用金额、收入目标 |
| 语义审查看不到指标定义 | 把正确的客诉 SQL 判成“无法区分客诉” | 把指标定义传给审查 |
| 提示词示例写了 `COUNT(*)` | 与校验要求的 `COUNT(列)` 矛盾 | 示例改成 `COUNT(t.id)` |
| 单表查询不写表名前缀 | 校验认不出是哪一列 | 只有一张表时可以确定，允许不写 |
| 模型不知道费用类别的取值 | 把“销售差旅”猜成“差旅” | 补充类别列表 |

### 为什么补登记，而不是放松校验

如果允许不声明指标的查询直接放行，模型就可能不声明指标，绕开“必须是已交付订单”这类强制条件（决策 D25）。你已决定暂不开放（决策 D26）。

### 毛利公式的校验

毛利的公式写错一个符号，结果就全错，所以校验会比对公式本身：

```python
"line_amount - unit_cost * quantity"     # 通过
"line_amount - quantity * unit_cost"     # 通过（乘法交换）
"line_amount + unit_cost * quantity"     # 拒绝
"(line_amount - unit_cost) * quantity"   # 拒绝
```

这样比较严格，模型换一种等价写法（比如分开写两个 `SUM`）也会被拒绝，然后获得一次修正机会。

### 修复过程中抓到的新问题

第 3 轮评测出现了一个真实的错误：

```sql
SELECT COALESCE(SUM(sales_orders.total_amount), 0) ...
```

`COALESCE` 把空结果改写成 0，于是“不存在的区域”的销售额变成了 0。这是把“查不到”说成“销售额为 0”，会误导决策。

| | 修改前 | 修改后 |
|---|---|---|
| `COALESCE(SUM(x), 0)` | 通过校验 | 拒绝，并提示模型修正 |

```python
if aggregate.find_ancestor(exp.Coalesce) is not None:
    continue    # 这个聚合不算满足指标要求
```

**为什么 `COUNT` 的 0 没问题：** `COUNT` 没有数据时返回 0，这本身就是真实结果。

### 结果

| 轮次 | 代码状态 | 通过/总数 | 放行错误数字 |
|---|---|---|---|
| 基线 | 未修复 | 13/19 | 0 |
| 第 2 轮 | 补登记指标，新增 5 道留出题 | 19/24 | 0 |
| 第 3 轮 | 加上审查修复 | 20/24 | **1**（`COALESCE`） |
| 第 4 轮 | 加上 `COALESCE` 校验 | 22/24 | 0 |

部署后的真实任务：毛利 2259844.98、客诉数量 0，都与标准答案一致。

### 怎么看待这些数字

- **不要只看 22/24。** 第 3、4 轮的代码差异很小，部分变化可能只是模型的随机波动。比如“平均订单金额”这题，基线和第 2 轮通过，第 3 轮未通过，第 4 轮又通过。
- **最可信的独立成绩是第 2 轮新留出题的 4/5。** 之后我根据其中一题补了费用类别，后面的 5/5 不再是独立检验。
- **修改规则后要重新看安全指标。** 第 3 轮通过率上升的同时，就出现了错误数字。
- **“放行错误数字为 0”有前提。** 演示数据测不出部分错误，比如漏写状态条件。
