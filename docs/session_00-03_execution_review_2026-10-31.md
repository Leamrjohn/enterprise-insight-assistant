### 3.2 建立可重复运行的冒烟执行器

复用现有开发用例和评分器，固定 8 题：3 道数据、3 道知识、1 道混合、1 道澄清。

主要文件：

- `backend/scripts/evaluation/run_smoke_tests.py`：通过 HTTP 登录、创建会话、提交问题、轮询结果并记录分类。
- `backend/scripts/evaluation/smoke_runtime_identity.py`：采集源码、镜像、模型参数、数据及语料指纹。
- `backend/tests/scripts/`：执行器、续跑、身份一致性与停止边界的离线回归。
- `docs/smoke_results/` 与 `artifacts/smoke/`：人可读报告与原始事件。

逐步补齐的行为：

- 一次命令只跑一轮；使用独立运行编号，拒绝覆盖已有新运行。
- 续跑要求原身份一致、上一轮完整、无缺题或重复题。
- 记录代码提交、容器源码、模型配置、语料版本、经营数据指纹、耗时和费用。
- 区分成功、失败、无响应、结果错误；符合预期的澄清和部分结果可算成功。
- 先识别待人工复核，避免把它当作仍在运行而超时取消；随后按你的选择，保留非成功分类并继续后续题。
- 跳过待复核任务的终态评分，避免错误调用评分入口引发 ValueError。
- 第二轮异常暴露后，再补上逐题停止：普通非成功结果阻止下一题提交，待复核仍继续。

最终执行器仍为 300 行。最近的执行器/身份测试 **26 项通过**，分类自检 **5 条通过**。这些是离线模拟验证，不是 26 次真实模型成功。

### 3.6 定位并修复任务 185 的复核输入缺失

第二轮数据题预算耗尽后，读取检查点和模型账本，确认调用链为：

`Planner → 计划语义复核 → SQL 生成/复核两轮 → Reviewer 返回部分结果 → Smart Router 重新规划 → 调用预算耗尽`

关键证据：

- Data 记录为 `sql_semantic_unsupported`，SQL 执行次数 **0**。
- SQL 生成器收到了现有受控定义 `EAST＝华东`；SQL 语义复核器只有表、字段和关联，缺失该定义。
- 复核器据此反复指出“华东到 EAST 的映射未验证”。预算耗尽是下游结果，不是首先应提高预算的理由。

你授权后，修改 `semantic_review_service.py`，仅给 SQL 复核载荷增加当前快照允许的表/字段对应的受控映射；不改变 AST、权限、评分期望及模型拒绝决策。

验证：新增测试先失败、修改后通过；SQL 复核测试 **13 项通过**，关联测试 **42 项通过**，Ruff 通过。合计 55 项仅属于本工单选定的离线测试，不能与历史 928 项相加称为当前全量覆盖。

## 5. 执行过程中我做得不够好的地方

1. **费用和变更授权多次打断推进。** 独立授权本身符合项目规则，但自动续行反复触发相同询问和 blocked 状态，沟通重复、效率不好。没有把自动续行当作新的付费授权。
2. **“异常停止”最初没有落实为逐题程序门禁。** 第二轮首题失败后，人工监控与终止存在延迟，实际已提交到第 4 题。这不满足严格的“首个异常后不再提交”；后来补了离线回归和停止条件，不能倒推当时没有问题。

4. **临时测试账号凭证生命周期不支持后续人工审批。** 造成任务 176 批准后还要单独恢复登录凭证；最终在你授权后重置隔离账号完成审批，未绕过权限。
5. **多次“测试通过”范围有限。** 局部测试通过、容器启动、审批成功、完整业务基线，是不同证据；本会话并没有靠其中任何一项证明所有计划完成。
