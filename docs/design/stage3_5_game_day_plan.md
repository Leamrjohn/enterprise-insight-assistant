# 工单 3.5：故障演练方案（2026-11-01，待用户选择）

## 目的
在真实运行的系统上制造故障，确认“设计上说会恢复”的地方真的会恢复；每一项都记录“期望行为 / 实际行为 / 是否修复 / 对应的自动化测试或手册条目”。

## 环境约束（调查结论）
- 本地模拟网关只返回固定文本，Planner 第一步就失败，任务无法“跑到一半”。
- `worker-test` 也读取真实模型配置，同样会产生费用。
- 因此要么接受少量真实模型费用，要么先搭一个“脚本化模拟模型”的隔离演练环境。

## 两个选项

| | A：主环境真实演练（推荐先做） | B：先搭隔离演练环境 |
|---|---|---|
| 做法 | 在现有 13 个服务上逐项制造故障，用真实模型跑少量任务 | 新增演练用 compose profile（API/Worker 指向测试库）+ 能返回合法 Planner/SQL/Reviewer 输出的脚本化模拟模型 |
| 费用 | 约 10–12 个任务 × 约 $0.003 ≈ $0.04，硬上限 $0.10 | 0 |
| 真实度 | 最高：真实模型延迟、真实队列 | 中：模型行为是脚本化的 |
| 工作量 | 小 | 大（新服务配置 + 模拟器，需新增配置项） |
| 影响 | 演练期间前端/API 会短暂不可用；任务写入平台主库（与冒烟相同） | 不影响主环境 |
| 适合 | 本次阶段 3 出口 | 阶段 9 的 CI 自动演练 |

推荐 A：一次性、低成本、最真实；B 的价值在于“每次提交都自动跑”，放到阶段 9 更合适。

## 演练项（两个选项相同）

| # | 故障 | 制造方式 | 期望行为 | 检查方法 |
|---|---|---|---|---|
| 1 | Worker 中途被杀 | 任务进入 running 后 `docker kill agent-worker-1`，再启动 | 租约过期后 `recover_expired_analysis_executions` 把任务转 retrying 并由新执行接手；只产生 1 份报告 | 执行记录 2 条、报告 1 份、事件序号连续 |
| 2 | Redis 停止时提交任务 | `docker stop agent-platform-redis` 后发消息，再启动 | 任务与 Outbox 已入库；Redis 恢复后发布器补投并完成 | Outbox 状态 pending → worker_claimed |
| 3 | 运行中 Redis 断开 | 任务 running 时停 Redis 30 秒 | Worker 不崩溃或可恢复；任务最终终态明确 | 终态与日志中的错误类型 |
| 4 | PostgreSQL 重启 | 任务 running 时 `docker restart agent-platform-postgres` | 连接池重连；任务重试或明确失败，不卡死 | 终态、健康检查恢复时间 |
| 5 | 模型超时 | 临时把 `LLM_TIMEOUT_SECONDS` 调到 1 并重启 Worker | 分类为可重试，带抖动重试，超过次数后 failed 并说明原因 | 重试次数、间隔不相同 |
| 6 | 重复投递 | 对同一 task_id 手动再投递 2 次 | 只有 1 个执行；被拒投递不报错（3.2 已修复） | 执行记录 1 条、无异常日志 |
| 7 | 两个 Worker 抢同一任务 | 临时扩到 2 个 Worker 并同时投递 | 只有 1 个执行 | 同上 |
| 8 | 取消运行中任务 | 任务 running 时调用取消接口 | 不再写结果（H5） | 任务 cancelled、无报告 |

停止条件：任何一项出现重复报告、取消后写入、旧执行覆盖新结果（H4/H5/H6），立即停止并汇报；费用到 $0.10 立即停止。
演练后：恢复所有配置与容器，确认 13 服务运行、readiness ok、无遗留 queued/running 任务。
