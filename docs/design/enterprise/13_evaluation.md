**状态：** 设计稿，未实现。文中配置是草案。对应总计划工单 B14、B15（并服务 E10）。

**不变的约束：** 不为通过测试改期望值；改期望和基线要用户批准；批量付费运行要先报次数和费用。

## 1. 现在怎么运行

| 类型 | 脚本 | 题目 | 费用 |
|---|---|---|---|
| 冒烟 | `run_smoke_tests.py` | 10 题 | 约 $0.025/轮【记录】 |
| 业务评测 | `run_business_evaluation.py` | `fixtures/evaluation/`（42 个文件） | 有费用 |
| 路由 | `run_planner_route_evaluation.py` | `evaluation_routing/` | 可回放 |
| SQL | `run_sql_result_evaluation.py` | `evaluation_sql/` | 可回放 |
| 检索 | `run_retrieval_evaluation.py` | `evaluation_retrieval/` | 本地免费 |
| 支持检查 | `run_support_evaluation.py` | `evaluation_support/` | 可回放 |
| 记忆 | `run_memory_evaluation.py` 等 | `evaluation_memory/` | 可回放 |
| 长对话 | `run_long_conversation_evaluation.py` | `evaluation_context/` | 可回放 |
| 工具 | `run_tool_selection_evaluation.py`、`run_tool_fault_drill.py` | `evaluation_tools/` | 可回放 |

**要保留的好设计：**
- 录音回放，找不到记录就失败，不会误付费（`replay.py`）。
- 冒烟记录身份哈希：代码、运行环境、题目、语料（`smoke_runtime_identity.py`）。
- 阈值先于运行固定（`thresholds.py:17`，`extra="forbid"`）。
- 区分开发集和留出集（`business_schemas.py:73`）。
- 结果错误也跑完一轮；费用超限会停止。

**存在的问题：**

| 问题 | 依据 | 实际后果 |
|---|---|---|
| 没有总报告 | 各脚本各自输出 | 不知道整体是变好还是变差 |
| 题目多由助手编写，答案待审核 | 【记录】`oracle_review` 多为 pending | 指标可能只是自说自话 |
| 留出集小且被多次看过 | 【记录】约 15 题 | 已不算真正留出 |
| 单次运行下结论 | 【记录】“旧策略 4/4 正常”后来被推翻 | 小样本误判，浪费排查 |
| 不比较逐题变化 | 只看总数 | 33→33 可能掩盖翻转 |
| 没进 CI | 见工程化设计 | 改坏了不会被发现 |
| 没有真实问题 | 【记录】题目和语料都是合成的 | 不代表真实使用 |
| 错误类型未归类 | | 难以判断下一步该修哪里 |

## 2. 目标结构

```text
backend/evaluation/
    datasets/
        manifest.json         所有题集的注册表
        routing/  sql/  retrieval/  knowledge/  memory/
        context/  security/  e2e/
    baselines/
        main.json             当前基线（CODEOWNERS 保护）
    suites.py                 pr / nightly / release 三组
backend/scripts/evaluation/run_all.py     统一入口
docs/evaluation_reports/                   报告
```

**现有题集分批迁入，内容不变。** 迁移时校验哈希相同。

### 2.1 题目结构

每题增加统一元数据：

```json
{
  "id": "sql-047",
  "suite": "sql",
  "split": "development",
  "question": "…",
  "expected": { },
  "tags": ["comparison", "time_range"],
  "source": "assistant_written",
  "review": {
    "status": "pending",
    "reviewer": null,
    "reviewed_at": null,
    "notes": null
  },
  "added_at": "2026-11-20",
  "version": 1
}
```

| 字段 | 取值 | 用途 |
|---|---|---|
| `split` | `development` / `heldout` / `regression` | 留出集不用于调试 |
| `source` | `assistant_written` / `user_written` / `real_sampled` | 报告按来源分别统计 |
| `review.status` | `pending` / `approved` / `rejected` | 只有 `approved` 才计入正式分数 |

### 2.2 留出集规则

```text
1 留出集文件单独存放；开发时的默认命令不运行它
2 只有发布前运行；每次运行写记录
3 报告只给通过率和错误类别，不给逐题错因（避免针对性调优）
4 每季度补充新题，并把旧题移入 regression
```

**没有技术手段能完全防止“看过”，** 所以靠流程，并记录运行次数。

## 3. 题目审核（B14）

**这是用户负责的部分，也是最好的学习方式。** 助手不能自己批准自己写的题。

```text
python backend/scripts/evaluation/review_cases.py --suite sql --limit 10
```

**每次看 10 题，每题回答：**

| 问题 | 选项 |
|---|---|
| 这题真实用户会问吗？ | 会 / 不太会 |
| 标准答案对吗？ | 对 / 错 / 不确定 |
| 判分标准合理吗？ | 合理 / 太严 / 太松 |

**结果写回题目的 `review` 字段并提交。** 不确定的题交给数据核对：用 SQL 独立算一遍答案。

**分批目标（以用户实际节奏为准）：**

| 批次 | 内容 | 题数 |
|---|---|---|
| 1 | 冒烟 10 题 | 10 |
| 2 | 路由 | 48 |
| 3 | SQL | 24 |
| 4 | Knowledge | 57 |
| 5 | 其他 | 余下 |

**审核前后的分数分开报告。** 分数变化可能是因为题目变了。

## 4. 不稳定性怎么处理

模型输出会波动，所以结果不能只看一次。

| 类型 | 运行次数 | 判定 |
|---|---|---|
| 确定性（校验、SQL 对抗、路由回放） | 1 次 | 必须通过 |
| 回放评测 | 1 次（录音固定） | 必须不低于基线 |
| 真实模型冒烟 | 至少 3 轮，切换策略时至少 5 轮 | 见下 |
| 单题波动调查 | 25 次 | 给出错误率和区间 |

**统计方式（代码计算）：** 每题给出通过次数和 95% 区间（Wilson 区间，样本小时比简单百分比可靠）。

```text
证据题  旧策略 8/9 通过，区间 57%～98%
        新策略 2/4 通过，区间 15%～85%
结论    区间重叠，不足以判断
```

**这正是之前的真实情况。** 有了区间，就不会把“4/4 正常”当成结论。

**逐题比较：** 报告必须列出翻转的题：

| 题 | 基线 | 本次 | 变化 |
|---|---|---|---|
| sql-047 | 3/3 | 1/3 | **下降** |
| know-012 | 1/3 | 3/3 | 上升 |

**判定规则：**

| 情况 | 结论 |
|---|---|
| 硬门禁有失败 | 拒绝 |
| 总分下降超过阈值 | 拒绝 |
| 总分不变，但有明显下降的题 | **不算通过**，要解释 |
| 确定性套件有失败 | 拒绝 |
| 只有波动题变化，区间重叠 | 记录，继续观察 |

## 5. 错误归类

每个失败都归到一个类别，并指向最上游节点：

| 类别 | 判定依据 | 去哪修 |
|---|---|---|
| `route_wrong` | 路由不符 | Planner |
| `clarify_wrong` | 该问没问，或不该问却问了 | Planner 规则 |
| `sql_wrong_answer` | 结果和标准不同 | SQL、语义层 |
| `sql_rejected` | 正确 SQL 被拦 | 校验 |
| `retrieval_miss` | 答案没进前 K | 检索 |
| `context_dropped` | 检索到了，没进提示词 | 上下文 |
| `answer_wrong` | 进了提示词，答错 | Knowledge 提示词 |
| `over_removed` | 支持检查删错句 | 支持检查 |
| `qualification_lost` | 限定丢失 | Reviewer |
| `validation_false_reject` | 校验误杀 | 校验 |
| `infra` | 超时、依赖故障 | 平台 |
| `budget` | 预算不够 | 预算或上下文 |

**这直接回答“修哪里”。** 现有观测数据（`evaluation/observation.py`）已能提供大部分信息。

## 6. 一条命令和总报告（B15）

```bash
python backend/scripts/evaluation/run_all.py --suite pr
```

| 套件 | 内容 | 费用 | 何时运行 |
|---|---|---|---|
| `pr` | 确定性、对抗、回放 | 0 | 每个 PR |
| `nightly` | 检索（本地）、全量回放 | 0 | 每天 |
| `release` | 冒烟 3～5 轮、付费评测、留出集 | 有，先批准 | 发布前 |

**运行前先显示费用估算：**

```text
本次将运行：冒烟 3 轮 + Knowledge 57 题
预计 2100 次模型调用内，费用约 $X
需要 --approve-cost 才会运行
```

**报告内容（Markdown + JSON）：**

```text
身份    提交、提示词组、配置档、语料、题集哈希
总览    每套件分数，和基线比较，门禁结果
硬门禁  跨公司、写库、绕过校验（必须 0）
翻转    下降和上升的题
类别    错误类别分布
波动    不稳定题和区间
成本    token、费用、耗时 P50/P95
范围    只算已审核题 / 全部题，分开给
没覆盖  这次没跑什么
```

**写入 `docs/evaluation_reports/`，文件名含提交和时间，不覆盖旧报告。**

### 基线怎么更新

```text
1 跑 release 套件
2 PR 里提交新基线 + 报告 + 变化原因
3 用户批准（CODEOWNERS）
```

**基线只能在“确实变好”或“题目修正并写明理由”时更新。**

## 7. 组件指标

| 组件 | 指标 |
|---|---|
| 路由 | 准确率、错误反问率、漏反问率 |
| SQL | 结果正确率、放行错误数字（必须 0）、过度拦截率 |
| 检索 | Hit@K、MRR、答案进前 K、答案进提示词、陷阱题 |
| Knowledge | 正确率、引用正确率、错误拒答率、错误回答率 |
| 上下文 | 约束保留率、超预算次数、token |
| 记忆 | 见记忆设计第 11 节 |
| 工具 | 工具选择率、无效调用率、故障演练结果 |
| 报告 | 数字绑定错误（必须 0）、限定保留率、`partial` 原因分布 |
| 安全 | 对抗集（必须全拦） |
| 成本和性能 | 单任务费用、P95 耗时 |

**端到端总分：** 按题型加权的“答案可接受率”，权重写进配置；**总分只作摘要，不能替代门禁。**

## 8. 真实问题回流（上线级，先留接口）

上线后才有真实问题。流程预留：

```text
用户点“没帮助” → 记录任务号 → 脱敏 → 人工判断 → 归类
→ 需要的话写成新题（source=real_sampled）→ 进入 regression
```

**没有用户授权和脱敏不能把真实内容写进题集。** 现阶段可以由用户手写“业务上真实会问的问题”，`source=user_written`，这对纠偏很有价值。

## 9. 失败路径

| 场景 | 系统行为 |
|---|---|
| 回放找不到录音 | 失败并提示“请求已变化，需要重新录制” |
| 付费运行中超费用上限 | 停止，保存已完成部分，报告标记不完整 |
| 脚本中断 | 按 `run_id` 续跑（冒烟已有 `--resume`） |
| 题集哈希和基线不同 | 拒绝比较，提示先更新基线 |
| 模型服务故障 | 归入 `infra`，不计入质量分，报告单独列出 |

## 12. 怎么确认它真的生效

| 检查 | 通过标准 |
|---|---|
| 一条命令 | 得到总报告，含没覆盖的内容 |
| 故意改坏提示词 | 报告指出下降的题和类别 |
| 总数相同但题目翻转 | 判定不通过 |
| 改基线不走批准 | CI 拒绝 |
| 费用超限 | 自动停止 |
| 查任一结论 | 能追到题目版本、提交和运行记录 |

**评测本身也可能有错。** 之前判分器把“不低于”的“不”当否定（`docs/worklog.md`）。所以判分函数也要单独测试，人工定期抽查已判通过的题。

**仍需开工时确认：** 各题集现有结构的差异（迁移难度）；`observation.py` 是否足以判定所有错误类别；Wilson 区间实现可用标准库完成，不新增依赖；CI 中需要嵌入模型的评测耗时。
