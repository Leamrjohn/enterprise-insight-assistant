## 1. 终点：做到什么程度

### 1.1 一句话目标

把“企业经营洞察助手”改到**本机可验证的企业级标准**：每条企业标准都有自动化测试或演练记录作为证据；同时你学会独立设计、实现和验收这类 Agent 模块。

### 1.2 两级范围

| 级别 | 含义 | 本计划怎么处理 |
|---|---|---|
| **本机级** | 在这台电脑上能验证 | **必须做完**，每项都有证据 |
| **上线级** | 需要真实环境：多机高可用、对接真实 SSO、密钥管理服务、WAL 归档、防篡改审计、合规（个人信息保护法、数据出境） | 只设计接口，不声称已具备；在上线就绪评审第二部分逐项列出差距 |

**本计划不等于通过 SOC 2、ISO 27001 等认证。**

### 1.3 企业标准和验收证据

整个计划的终点是 R10 的“上线就绪评审”，分两部分：
1. **本机级证据：** 下表 12 条逐条拿出本次运行的证据。
2. **上线级差距清单：** 第 1.2 节上线级的每一项，写明现在留了什么接口、真正上线时要做什么、由谁决定。

**评审结论分开记录两件事：**
- **评审已出结论：** 每条标准都有证据，或者写明差距和原因。
- **本机级已达标：** 12 条全部有通过的证据。

只有第二件成立，才算到达本计划的终点。没达标的标准回到对应段补，不能用“写明差距”代替。

## 2. 总体做法

### 2.1 不变的约束（任何工单都不能违反）

- **主链：** API 写任务和 Outbox → Worker 认领 → Planner → Data / Knowledge → Reviewer → 确定性校验 → 持久化发布。
- **经营库只读**；SQL 必须过 Schema 和 AST 校验；所有查询限定在当前公司和任务范围内。
- **最终能否发布由确定性校验决定**，Reviewer 不能替代它。
- 租约、检查点、恢复机制保留；记忆不当证据；文件上传入口保持冻结。

### 2.2 架构形态

继续用**模块化单体**：一个代码库内分清模块边界，不拆微服务。理由是单人开发、并发还没测出瓶颈，拆分只会增加运维成本。

```text
接入层     API │ 身份 │ 限流配额 │ 准入
控制层     任务/Outbox │ 租约恢复 │ 主链编排 │ 策略快照
Agent 层   Planner │ Data │ Knowledge │ Reviewer │ 确定性校验
平台层     工具平台 │ 上下文引擎 │ 记忆平台 │ 模型网关 │ 提示词注册表 │ 配置与策略
数据层     平台库(RLS) │ 公司经营库(只读) │ 向量/全文 │ 对象存储 │ Redis
横切       遥测(trace/指标/日志) │ 审计 │ 评测门禁 │ 数据分级
```

依赖方向用工具强制（E4）：接入/控制 → Agent → 平台 → 数据。

### 2.3 每个模块的固定 7 步

| 步 | 做什么 | 谁主导 | 产出 | 怎么算完成 |
|---|---|---|---|---|
| 1 体检 | 用数字量出现在哪里是 demo 水平 | 共同 | 基线表 | 每个问题有代码位置或测量数字 |
| 2 方案课 | 讲 2～4 种主流做法和代价；**写“引入还是自建” ADR**（见第 4 节清单） | 我讲 | 方案对比表、ADR 草稿 | 不超过一页 |
| 3 选型 | 你选方案并写理由，我指出漏项 | **你** | ADR 第 7 节“决定” | 理由落到本项目事实上 |
| 4 定指标 | 成功标准、评测题、留出题；同时审这一模块的评测题 | **你**主导 | 指标和题集 | 题目经你审核 |
| 5 实现 | 按工单分类进行 | 按类型 | 代码和测试 | 每个工单过自己的验收 |
| 6 实验 | 对照、隔离变量、算够样本 | **你**分析 | 实验结论 | 按题比较，不只看总数 |
| 7 上线复盘 | 开关、灰度、回滚；记录问题和解法 | **你**写 | 复盘一页、运行手册 | 写清怎么开关、怎么回滚、出错先看哪里 |

**模块完成的标准：** 工单全部完成或明确推迟并写理由；指标达标或如实写明差距；有运行手册；你能不看资料讲清设计、取舍和一次真实问题的解决过程。**平台模块（上下文、工具、记忆、网关）完成时，同时上报本模块的指标**，不留到 R10 再补。

### 2.4 工单三类

| 类型 | 判断标准 | 你做什么 | 我做什么 |
|---|---|---|---|
| **训练** | 核心算法、判定规则、关键测试 | 按放手阶梯动手 | 骨架、评审 |
| **共建** | 有设计选择，但代码量大或风险高 | 定方案、看关键改动、验收 | 实现 |
| **代做** | 机械性工作：搬移、配置、依赖、样板代码 | 只看结论 | 全部 |

每个模块至少 2 个训练工单，而且是这个模块最核心的部分。

### 2.5 每个工单怎么进行

1. 先用 2～3 行复述目标和验收标准；**同时核对它在路线里的位置和前置工单是否完成。**
2. 只读与工单有关的文件。
3. 先复现失败现象，再修改，再验证。
4. 一个工单一个主题、一个提交；顺手发现的问题写进 worklog 待办。
5. 验证从小到大：针对性测试 → 冒烟测试 → 全量测试。
6. 同一思路连续失败 2 次就停下汇报。

**必须先问你的：** 删除或重建数据库；改表结构的迁移；新增或移除依赖；改主链结构、权限逻辑、SQL 校验；改测试期望；一次超过 10 个文件或 400 行；有明显费用的模型运行；任何 git 历史改写。下文工单表“批准”一列标出了已知需要批准的工单。

### 2.6 怎么提升指标（每个模块第 6 步）

```text
1 基线    同一提交、同一题集，跑出当前数字
2 归类    把失败按最上游原因分类
3 选目标  先处理最大的一类，而不是最容易修的
4 假设    “如果改 X，Y 类错误应该减少”
5 单变量  一次只改一处
6 样本    先算需要多少次才能区分，再决定跑多少次
7 判定    按题比较，看翻转和区间
8 记录    无论成功还是失败，都写进复盘
```

### 2.7 分支和集成

**现状：** 工作分支 `work/smoke-baseline` 比 `main` 多 282 个提交，`main` 最后一次提交是 2026-07-05，这些提交从没在 CI 上跑过。计划文档的提交在 `docs/adr-gateway-observability` 分支上，工作分支里还没有。

**规则：**
1. **现在：** 文档分支确认后合回工作分支，不再让计划和代码分在两条线上。
2. **E1 之前：** 所有工作继续在工作分支上做，不再新开长期分支。
3. **E1 完成后：** `main` 是唯一主线。每个工单从 `main` 开一个短分支，CI 全绿后合并，合并后删除分支。
4. 不改写已推送的历史；推送和合并 `main` 都要你批准。

### R1 测量、观测、配置治理和推送门禁

**做到什么程度：**
- 代码进 CI，`main` 是可发布主线；同一提交两次构建依赖完全一致。
- **最小发布门禁：** 路由、SQL、Knowledge 的现有离线或回放评测接进 CI，下降就失败；从第一个迁移工单起，每个迁移都验证升级、回退、再升级。R8、R10 再补齐完整门禁。

## 7. 风险和不做的事
