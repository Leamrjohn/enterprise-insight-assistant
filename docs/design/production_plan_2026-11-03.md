## 1. 一页结论

**整体判断。** 这个项目的安全边界和审计底子不错：有权限校验、SQL 多层防线、模型费用账本、租约恢复和故障演练。离生产级的主要差距不在“缺模块”，而在四件事：

1. **回答质量的地基有隐患。** 切分器对中文基本不起作用，向量检索只看到文档开头。现有评测是文档级的，语料又短，所以没暴露。
2. **回答不稳定，而且查不清原因。** 模型的原始回答没有保存，关键日志字段此前也被丢弃，所以“丢句”“限定为空”只能靠猜。
3. **运营能力缺失。** 没有指标系统和告警，限流实际上没有生效，镜像依赖没有锁定版本。
4. **部分保护只在关闭的路径上。** 熔断和重试只接在默认关闭的“模型选工具”模式上，主链没有。

**最值得先做的三件事：**

|---|---|---|
| 1 | 把冒烟跑稳，查清“质量题限定为空” | 这是 `AGENTS.md` 当前阶段的任务，也是后面所有回归的尺子 |
| 2 | 按真实长度重做切分（RAG） | 影响所有文档题，见第 7 节的实验数据 |
| 3 | 按问题切换模型参数，并保存脱敏的模型原文 | 同时改善稳定性和可排查性 |

### 差距和实际后果
| 差距 | 实际问题 |
|---|---|
| 没有统一工具登记表 | 加一个工具要改 4 处以上，漏一处就出现权限或契约不一致 |
| 主链没有熔断 | 业务库或检索故障时，每个任务都要等到超时才失败，故障时排队更严重（未验证） |
| 没有通用的超时和结果大小限制 | 新工具如果忘了设置，可能拖住 Worker 或塞爆上下文 |
| 审计次数少于实际执行次数 | 排查和计费时对不上 |

### 目标设计
- **工具登记表**：一个工具只在一处声明名称、版本、参数契约、允许角色、超时、结果上限、是否可重试、模型说明。其他地方都从这里读。
- **统一中间层顺序**：权限 → 参数 → 预算 → 熔断 → 超时 → 执行 → 结果截断 → 审计。每次实际执行都留记录。
- **错误分三类**：调用方的错（可让模型修正）、基础设施的错（可重试、可熔断）、任务级停止信号（直接向上抛）。

### 优先级和验收
| 优先级 | 改进项 | 验收标准 |
|---|---|---|
| P1 | 主链接入熔断（改主链，需先问） | 停业务库演练：熔断打开后任务在 5 秒内明确失败，恢复后自动放行 |
| P1 | RAG 失败补错误码 | 检索、嵌入、未知错误各有独立错误码；有单元测试 |
| P2 | 工具登记表 | 新增一个假工具只改一处，所有契约测试通过 |
| P2 | 审计记录每次实际执行 | 故障注入重试 1 次，审计出现 2 条 |
| P3 | 工具循环接上下文预算（切换工具模式前必做） | 构造 6 轮大结果，单次请求不超预算 |

**建议继续关闭工具模式。** 记录显示费用约 1.7～1.8 倍，准确率没有提高，模型自选路线 36～37/48，低于 Planner 的 43/48。【记录】

- **模型层熔断和备用模型**，切换后在报告里标注。
- **发送前数据分级**：按公司设置决定哪些字段可以外发。
- **账单核对**：每天对账，差异超过阈值就告警。

### 关键发现
1. **切分器对中文基本不起作用。** 它用空格数词（`document_chunk.py:29`），中文几乎没有空格，512 的上限永远达不到。现有语料 154 篇切出 154 个片段，也就是每篇都没切，中位长度 1036 字。【运行】
2. **向量模型只读前 128 个 token。** `paraphrase-multilingual-MiniLM-L12-v2` 的上限是 128，约等于 220 个中文字。99.4% 的片段超过这个长度。实测保持开头不变、只改后面的内容，相似度仍是 0.9999998，说明后面的内容对向量没有影响。【运行】
3. **现有评测测不出这个问题。** Hit@3 是文档级的，语料每篇只有约 1000 字，开头通常就写明了主题。
4. **证据常被提前丢弃。** 提示词证据上限 3000 字，超过就直接停止（`engine.py:52`、`:76`）。随机抽 3 篇语料，60.5% 超限，第三份证据经常进不了提示词。【运行：按文档长度估算，未统计真实任务】
5. **带入已确认事实会污染检索问题。** 有事实时，这些语句会拼进检索文本（`knowledge/schemas.py` 的 `render_query`）。【代码】检索词变长后更容易被 128 上限截断，实际影响未验证。
6. **没有实体和编号的精确过滤。** “SUP-012 的质量评分”这类题依赖关键词和语义碰运气。【运行：见下方错题】
7. **裁判环节有随机性，而且结果影响很大。** 逐句检查模型判错就删句（`support.py:160`）；结论边界要求逐字一致（`reviewer_agent.py:212`）。这是冒烟不稳定的直接来源之一。【记录】

### 目标设计
- **分层检索（small-to-big）**：用短片段做匹配，保证向量看得全；用它所在的小节或相邻片段做重排和回答，保证上下文够。
- **每段带文档头信息**：标题、编号、实体、日期；表格切分时保留表头。
- **确定性问题理解**：代码提取编号、客户名、月份，用作过滤或加权，不靠模型猜。
- **证据预算按句挑选**：超限时跳过放不下的证据继续选，不直接停止；同一文档的片段合并。
- **检索问题和事实分开**：检索只用问题本身，事实只用于回答。
- **回答结构化**：答案按子问题分条，每句带引用，并单独列出“结论边界”，这样不用事后再靠模型从文档里找限定。
- **裁判节点温度 0**；结论边界比较时统一空白和 Markdown 符号（改校验逻辑，需先问）。

### 怎样综合提升“回答正确率”
正确率是整条链路的结果，路由错了，后面全错。所以建议建立一个总分：同一批题走完整主链，按“回答类型正确、数字正确、引用正确、该拒则拒”判分，再按错因归到路由、检索、SQL、生成、裁判。这样每次先修占比最大的错因。
