# 总览：从“能跑”到“接近生产级”的执行计划

## 1. 怎么使用本计划

- 分工：Codex 执行；用户决策并验收；Claude 审查 Codex 的汇报并讲解。
- 每次只做一个工单（编号如 3.2）。给 Codex 的指令固定为：
  “先读 AGENTS.md，再读 docs/roadmap/00_overview.md 的第 1～3 节，以及 docs/roadmap/0X_xxx.md 中的工单 N.M，按其执行。不要阅读其他阶段。”
- 每个阶段的第一个工单一律是“只读调查”：先核对项目里已经有什么、哪些已被验证，已有且验证通过的不重做。本计划是在没读源码的前提下写的，具体细节以调查结果为准。
- 每个工单结束后，用户把 Codex 的汇报发给 Claude 审查，并用自己的话回答“检查题”。

### 工单模板
每个工单包含：目标｜前置条件｜步骤｜验收（用户自己能看到）｜证据要求｜停止条件｜学习点｜检查题。

## 2. “接近生产级”在本项目的含义（单机、不上线）

**要做到**：像对待真实线上系统一样设计、测试、演练和记录，每个性质都要有可重复的证据。
**不做**：多机高可用、Kubernetes、真实流量 SLO、合规认证、真实客户数据。

| 维度 | 要达到的性质 | 证据形式 |
|---|---|---|
| 正确性 | 数据类答案与独立参考答案一致；报告里的每个数字可追溯到查询结果 | 评测集（开发集加留出集） |
| 安全与隔离 | 跨公司零泄漏；经营库只读；提示词注入不生效；密钥不入库不入日志 | 对抗测试集 |
| 可靠性 | 崩溃、重试、取消、重复投递、依赖故障下结果仍正确、不重复 | 故障演练表 |
| 可观测 | 任意一个任务都能还原“每一步做了什么、花了多少” | trace 命令 |
| 性能与成本 | 每个任务有耗时、token、费用上限，超限有明确终态 | 基线数据与预算测试 |
| 可测试 | 分层测试，门禁自动执行 | CI 与测试清单 |
| 可运维 | 一键启停、健康检查、故障手册、备份恢复演练过 | runbook 与演练记录 |
| 变更管理 | 迁移可前滚、可回滚；依赖和镜像版本固定；配置与密钥分离 | 迁移测试、锁文件 |
| 数据管理 | 有备份、保留与删除策略，测试数据可重建 | 恢复演练 |
| 可理解 | 用户能解释主链并排查常见故障 | 口试与毕业演练 |

### 硬门禁（任何时候都必须为 0，且必须有自动化测试）

| 编号 | 门禁 | 主要在哪个阶段建立测试 |
|---|---|---|
| H1 | 未授权的跨公司或任务范围外数据 | 4、6、8 |
| H2 | 经营库被写入 | 4 |
| H3 | 报告出现无来源的数字或无证据的确定性归因 | 5、8 |
| H4 | 同一任务产生重复报告 | 3 |
| H5 | 取消后仍写入结果 | 3 |
| H6 | 旧 Worker 覆盖新结果 | 3 |
| H7 | 绕过确定性校验发布 | 5、8 |

## 3. 全局工作规则（保证 Codex 稳定的关键）

- R1 一次一个工单。改动不超过 10 个文件、400 行，超了拆成两个工单。
- R2 先验证再重做：已有能力先用测试证明可用，证明不了再改。
- R3 先测后改：先写出能复现问题的失败用例，再改代码，让它转绿。
- R4 一个工单一个提交，信息格式“[N.M] 一句话”；每个阶段结束打标签 stage-N-done。回退用 git revert，不改写历史。
- R5 前后对比：任何影响行为的改动，汇报里必须有同一条冒烟命令的“改前 / 改后”结果；变差就不合入。
- R6 三层验证，汇报必须写明本次验证到了哪一层、哪一层没覆盖：
  单元和契约测试（快）→ 真实依赖集成（真实 PostgreSQL 和 Redis）→ 端到端（HTTP、Worker、真实模型）。
- R7 同一思路连续失败 2 次，或工单用掉计划会话数的两倍，就停下来汇报。
- R8 不许改评测期望值、删除或跳过测试，除非用户批准并写明理由。
- R9 凡是会批量调用模型的运行，先报告预计次数和费用级别，等用户同意。
- R10 新增配置项必须有默认值、校验和 .env.example 说明；密钥不入库。
- R11 数据库迁移必须能前滚，并有降级方式或明确标注“不可逆”；执行前先备份。
- R12 每个阶段结束时更新 docs/worklog.md，不新增 evidence.md。

## 4. 阶段总览（会话数仅为估计，约 60 次）

| 阶段 | 主题 | 出口门槛 | 会话 |
|---|---|---|---|
| 0 | 工作区与环境 | 目录整洁、Git 干净、一键启停、测试能跑出真实数字 | 3 |
| 1 | 冒烟测试与基线 | 8 题 × 3 次的基线表，目标数值定稿 | 3 |
| 2 | 轨迹与可观测 | 任选一个失败任务，5 分钟内说出失败在哪一步 | 4 |
| 3 | 任务可靠性 | 故障演练表全绿；H4、H5、H6 有自动化测试 | 8 |
| 4 | 工具层与 SQL 防线 | 对抗集全部被拦；H1、H2 有自动化测试 | 6 |
| 5 | 数据正确性 | 数据类冒烟达标；留出集不明显落后；H3、H7 有测试 | 8 |
| 6 | 知识检索 | 检索指标达标；越权 chunk 为 0；引用可校验 | 8 |
| 7 | 上下文与记忆 | 长任务不丢目标；记忆隔离与删除测试通过 | 6 |
| 8 | 报告可信与安全 | 注入和隔离测试全绿；日志无敏感信息 | 7 |
| 9 | 运维与交付 | 备份恢复成功；CI 分层；soak 测试；毕业演练通过 | 8 |

**额度不够时按这个顺序保留**：0→1→2→3→4→5→8→9，其次 6，最后 7。阶段 6、7 可以缩小范围，但 3、4、5、8 不能砍。
**和之前口头给你的四阶段相比做了两处调整**：轨迹提前到阶段 2（没有轨迹就很难定位失败，修复会变成猜）；增加了可靠性、安全、运维三个阶段（这是“接近生产级”和“能演示”的真正区别）。

## 5. 目标数值（初始建议，阶段 1 结束后与 Claude 一起校准）

- 固定冒烟集（8 题 × 3 次）成功率：阶段 5 后 ≥ 90%，终验 ≥ 95%。
- 硬门禁 H1～H7：始终为 0。
- 故障演练：全部通过。
- 检索 Recall@5：以基线为准，初始期望 ≥ 0.85。
- 端到端 p95 耗时、单任务费用：以基线为准，上限设在基线的 1.5 倍内。

## 6. 学习机制（目标：理解全部内容，遇到真实问题有解题思路）

每个阶段固定四步：
1. 读：工单完成后，Claude 带你对着真实代码读调用链（函数 A → 函数 B，传什么，为什么）。
2. 复述：用自己的话回答工单里的“检查题”，发给 Claude 纠正。
3. 排错考题：Claude 现场给一个故障现象，你写出排查顺序（先看哪里、为什么）。
4. 出口口试：阶段末 5 道题，答得上来才算过关。

“掌握”的标准：不看资料能画出该阶段涉及的流程，能说出三个典型故障、症状和第一步排查动作。

## 7. 通用“出问题怎么办”

- Codex 改坏了：回到上个标签或用 git revert 单个提交；先备份再动。
- 冒烟变差：以前后对比为准，先回退，再分析。
- 同类问题反复：停下，把汇报发给 Claude，通常是上游有更根本的原因。
