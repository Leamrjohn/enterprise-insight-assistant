# 阶段 0～2：工作区与环境、冒烟基线、轨迹与可观测

---

## 阶段 0：工作区与环境

出口门槛：根目录整洁；`git status` 干净；一条命令启停环境；后端 lint 和非 e2e 测试有真实数字；打标签 stage-0-done。

### 0.1 目录与 Git 整理
- 前置：已建备份分支和补丁文件。
- 步骤：按“只读盘点 → 用户同意 → 执行”两步走（盘点表、分类 A/B/C/D、搬到项目外存档目录、写 restore 脚本、追加 .gitignore）。Git 已跟踪文件的路径不动，被 Docker 挂载或被脚本引用的路径不动。
- 验收：`git ls-files` 总数前后一致；`/health/ready` 正常；根目录一眼能数清。
- 学习点：已跟踪 / 未跟踪 / 被忽略；为什么移动被挂载的路径会让容器起不来（你已经亲眼见过）。
- 检查题：如果 docker-compose.yml 里有一个 bind mount 的主机路径被搬走，容器会发生什么？

### 0.2 规则与文档降级
- 步骤：换精简版 AGENTS.md；`docs/evidence.md`、旧路线图与旧计划移入 `docs/history/`；README 的文档导航改为指向 docs/roadmap/；新建 docs/worklog.md。
- 验收：新会话里 Codex 不需要通读 docs/ 就能开工。
- 检查题：为什么规则文件越长越容易让 AI 工具失效？

### 0.3 环境一键化与健康检查
- 步骤：
  1. 在 scripts/ops/ 下提供 `up` / `down` / `status` 三个脚本（`down` 绝不带 `-v`）；`status` 输出各服务状态和 /health/ready 结果。
  2. 修正数据库健康检查：确认是否因为用了角色名当库名而每 5 秒报 `database "agent_app" does not exist`，使用 `pg_isready -U <角色> -d <库名>` 或等价写法。
  3. 创建 .venv，运行 README 里的 lint 与不含 e2e/slow 的测试，记录通过数、失败数、失败测试名。
  4. 检查基础镜像、Python 与 PostgreSQL 的版本是否固定（不使用 latest）。
- 验收：三个脚本可用；测试结果有真实数字；日志里不再每 5 秒出现报错。
- 生产级要点：健康检查（liveness 存活 / readiness 就绪）的区别；依赖版本固定。
- 停止条件：失败测试超过 20 个时不要逐个修，先汇报分类。
- 检查题：存活检查和就绪检查分别在什么时候该失败？

## 阶段 1：冒烟测试与基线

出口门槛：`docs/smoke_results/` 里有一份可信基线；最上游的 3 个问题已归类；第 5 节目标数值定稿；打标签 stage-1-done。

### 1.1 只读调查
- 调查：现有评测用例、夹具、演示账号、已有 e2e 脚本能否复用；任务的结果状态有哪几种。
- 产出：一页“可复用清单”。

### 1.2 冒烟脚本（不超过 300 行）
- 选 8 题：数据类 3（必含 data-east-delivered-revenue-2025-08）、知识类 3、混合 1、应拒绝或应澄清 1。
- 走完整 HTTP 流程，每题 3 次，单次超过 180 秒算“无响应”。
- 结果分四类：成功 / 结果错误 / 失败 / 无响应；预期的拒绝或澄清算成功。
- 记录并输出：代码提交号、模型名与参数、数据版本、每次耗时、token 或费用。
- 生产级要点：基线必须可复现（固定种子、温度、数据）；记录环境信息，否则两次结果无法比较；不要把密码写进脚本。

### 1.3 运行基线与分类
- 授权最多 3 轮，第 1 轮先报耗时和费用，再决定是否继续。
- 非成功项按出错层归类：环境 / Planner / Data-SQL / Knowledge / Reviewer / 确定性校验 / 发布。
- 约定：另备 8 个“留出题”，由用户与 Claude 设计，不放进仓库，阶段 5 后用来检验是否对评测集过拟合。
- 学习点：为什么同一题要跑 3 次（不确定性）；开发集与留出集；为什么基线必须记录版本。
- 检查题：如果一道题 3 次结果是“成功、失败、成功”，你认为问题大概率出在哪一类？

## 阶段 2：轨迹与可观测

出口门槛：用户亲自选一个失败任务，用 trace 命令在 5 分钟内说出失败发生在哪一步、为什么；日志中没有密钥和个人数据；打标签 stage-2-done。

### 2.1 只读调查
- 调查：项目已有的任务事件、模型调用记录、工具调用审计、指标，能不能用一个 task_id 把整条链串起来？缺口在哪？
- 产出：一页“缺口清单”。

### 2.2 trace 命令
- 做一个命令行工具：给定 task_id，按时间线输出——状态迁移、每个步骤的耗时、模型调用（模型名、token、耗时、是否重试）、工具调用（名称、参数摘要、结果摘要、错误）、SQL（脱敏后的文本）、检索到的 chunk 编号、最终状态。
- 验收：你随便选一个冒烟失败任务，能指着输出说出“失败在第几步”。

### 2.3 关联 ID 与结构化日志
- 让 request_id、task_id、attempt 贯穿 API → Outbox → Worker → 模型调用 → 工具调用。
- 日志改为 JSON 一行一条，固定字段：时间、级别、组件、task_id、事件名、耗时。
- 测试：构造包含密钥格式、邮箱、手机号的输入，断言日志与 trace 中都被脱敏。
- 生产级要点：关联 ID 是排错的命脉；脱敏要有测试，不能靠人记得。

### 2.4 成本与耗时汇总
- 每个任务汇总：总耗时、各步骤耗时、token、估算费用；冒烟结果表增加这几列。
- 设定按步骤的耗时和费用基线，作为阶段 3 的预算依据。
- 学习点：trace（链路）、log（事件）、metric（指标）三者的区别；为什么先做 trace 再做修复。
- 检查题：一个任务“无响应”，你按什么顺序看 API 日志、队列、Worker 日志、trace？
- 口试：说出一个请求从 API 到报告写入数据库的主要环节；说出三个会让任务“卡住”的原因。
