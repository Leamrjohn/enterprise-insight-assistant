# 阶段 3～5：任务可靠性、工具层与 SQL 防线、数据正确性

## 阶段 3：任务可靠性

出口门槛：故障演练表全绿；H4（重复报告）、H5（取消后写入）、H6（旧 Worker 覆盖）有自动化测试且通过；打标签 stage-3-done。

### 3.1 只读调查：画出任务状态机
- 产出一页图：所有状态、每条迁移（谁触发、在哪张表、哪个函数）、哪些是终态。
- Claude 带你对着代码读一遍，你复述。

### 3.2 不变量与测试
把下面每条写成测试，至少一部分使用真实 PostgreSQL 并发执行：
1. 同一任务同一时刻最多一个有效执行者（租约）。
2. 终态不可回退。
3. 取消后不再写入结果（H5）。
4. 重复投递或重复点击不产生重复报告（H4，靠幂等键）。
5. 旧 Worker 的迟到结果不能覆盖新结果（H6，靠租约编号或围栏令牌）。
- 生产级要点：Outbox 保证“写库和发消息”一致；消息队列是“至少一次”投递，所以消费端必须幂等；认领任务用 `SELECT ... FOR UPDATE SKIP LOCKED` 一类的原子方式。
- 检查题：为什么“至少一次投递加幂等”比追求“恰好一次”更现实？

### 3.3 重试分类与死信
- 错误三类：可重试（限流、超时、5xx）、不可重试（参数或校验失败、权限不足）、需人工。
- 可重试用指数退避加随机抖动，设最大次数；超过进入明确的“失败（可重试耗尽）”终态，并保留原因。
- 测试：模拟每一类错误，断言重试次数与终态。

### 3.4 超时与预算
- 每个步骤超时、整个任务 deadline、token 或费用上限、最大步数。
- 超限的终态与给用户的提示要明确，不允许静默卡住。
- 测试：把上限调小，断言任务按预期终止。

### 3.5 故障演练（game day）
逐项制造故障，填写“期望行为 / 实际行为 / 是否修复”表：
- 任务中途杀死 Worker；
- 断开 Redis、断开 PostgreSQL、重启数据库；
- 模型接口超时、限流（429）、返回乱码或空结果；
- 同一任务被重复投递；两个 Worker 抢同一个任务；
- 磁盘接近写满的告警是否可见（可模拟）。
- 验收：演练表全绿；每个失败项都有对应的自动化测试或 runbook 条目。
- 口试：画出状态机；解释租约；说明 Worker 被杀后任务如何恢复；任务一直无响应时的排查顺序。

## 阶段 4：工具层与 SQL 防线

出口门槛：对抗集中的 SQL 攻击全部被拦且报错可读；H1（越权数据）、H2（写经营库）有自动化测试；打标签 stage-4-done。

### 4.1 只读调查与对照
- 调查：工具运行时的契约（注册、参数校验、错误信息、超时、截断、权限、审计、幂等）。
- Claude 带你把 tool_layer.py（教学版）与项目里的 tool_runtime.py 逐段对照，列出差距。

### 4.2 工具契约补齐与“模型常犯错误”用例库
- 用例库至少覆盖：不存在的工具名、缺参数、类型错、多余参数、枚举值错、结果过大、超时、工具内部异常、重复调用同一工具。
- 每个用例断言：被拦住、错误信息指导模型如何改正、有审计记录。

### 4.3 SQL 五层防线（每层都有独立测试）
1. 契约层：只允许单条 SELECT；模型输出必须是结构化意图加 SQL。
2. AST 层：白名单表、列、函数；拒绝多语句、写操作、系统 schema、危险函数（如 `pg_sleep`、大对象与文件读写类函数、`COPY`）。
3. 范围层：强制带当前公司和任务范围条件（行级安全 RLS）。
4. 执行层：只读数据库角色、只读事务、`statement_timeout`、行数上限、结果大小上限、并发上限。
5. 审计层：记录原始 SQL、改写后 SQL、耗时、返回行数，脱敏后存储。
- 生产级要点（纵深防御）：假设 AST 校验有漏洞，数据库角色权限和 RLS 仍然能兜住；两层要分别测试。
- 测试：用越权角色直接连库尝试写入和跨公司读取，必须失败。

### 4.4 对抗测试集（至少 50 条）
- 类别：注释绕过、多语句、大小写与编码、子查询或 CTE 写入、函数副作用、跨公司条件被篡改、超大结果、慢查询、系统表探测、注入式用户问题。
- 要求：每条都被拦住，拦截原因可读；任何一条放行都是 H1 或 H2 事件，必须立刻汇报。
- 学习点：纵深防御、最小权限、为什么不能靠提示词约束模型。
- 口试：说出 SQL 经过哪几层检查；如果 AST 层被绕过，还有什么保护？为什么提示词不能做权限控制？

## 阶段 5：数据正确性

出口门槛：数据类冒烟达标；留出集不明显低于开发集；H3（编造数字）、H7（绕过校验）有测试；打标签 stage-5-done。

### 5.1 复现并定位已知失败案例
- 对 data-east-delivered-revenue-2025-08：复现 → 取出模型生成的 SQL → 与参考答案对照 → 分层定位：Planner 理解错？Schema 快照缺字段？SQL 生成错？业务口径（“已交付”“东区”）不一致？校验放错行？
- 产出：一页定位报告，标注“已验证”或“推测”。

### 5.2 业务口径层（指标字典）
- 把“已交付收入”“东区”“某月”等写成明确定义：指标名 → 使用的表、过滤条件、时间口径、单位。
- 注入 Data Agent 的上下文，并保证有测试：同一口径无论怎么问都走同一定义。
- 生产级要点：“SQL 能执行”不等于“业务正确”，口径由人定义并版本化，不让模型每次现猜。

### 5.3 数据评测集扩充
- 覆盖：聚合、分组、时间区间、同比环比、空结果、歧义问题（应澄清）、越权问题（应拒绝）。
- 参考答案由独立的 oracle SQL 生成并人工复核；开发集与留出集分离，留出集由用户与 Claude 维护，Codex 看不到。
- 过拟合检查：开发集与留出集成功率差距超过约 10 个百分点要警惕。

### 5.4 数字落地校验（确定性）
- 报告中每个数字必须能对应到某次查询结果：数值、单位、口径都匹配；对不上就不能发布。
- 测试：故意构造“数字被模型改动”的报告，断言发布被拦（H3、H7）。

### 5.5 失败回流
- 流程：运行中发现的失败样例 → 复现 → 归类 → 补进评测集 → 修复 → 回归。
- 学习点：开发集与留出集、oracle、口径、确定性校验与模型审查的分工。
- 口试：为什么不能让 Reviewer 模型替代确定性校验？“SQL 能执行”为什么不等于“结果正确”？
