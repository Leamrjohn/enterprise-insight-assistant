## 阶段 2.5：组件评测台

出口门槛：一条命令离线跑完四类组件评测，并输出基线表；不调用付费模型的部分可以重复跑且结果一致。

### 2.5.1 只读调查
- 盘点 `backend/app/modules/evaluation/`（已有 retrieval、business、workflow、thresholds）和 `backend/tests/fixtures/evaluation/`（42 份素材），列出四类评测分别能复用什么。

### 2.5.2 检索评测
- 复用 `evaluate_retrieval`，补充 MRR、Recall@k（k=3、5、10）；固定嵌入模型和语料，测出基线。

### 2.5.3 SQL 与路由评测
- SQL：给定问题和固定计划，比较执行结果与 oracle 结果（用结果指纹比较，不比较 SQL 文本）。
- 路由：问题 → 期望的 action / route。
- 模型输出可以录制下来回放：录制一次（需批准费用），之后离线重放，免费且结果可复现。

### 2.5.4 报告校验评测
- 构造一组“数字被改”“引用越权”“因果无证据”的报告，统计拦截率，要求 100%。
- 学习点：组件评测和端到端评测的分工；录制回放为什么能省钱、能复现。
- 检查题：端到端成功率不变、但检索召回率下降，这说明什么？

## 4.5 模型自主选择工具（影子模式）

目标：学会“在很多工具中让模型知道什么时候调哪个”，同时不破坏现有的固定工作流。
- 影子模式：新节点只记录模型会选哪个工具，不影响真正执行的路线；改主链前必须用数据证明它更好，并征得用户同意。

步骤：
1. 工具描述规范：每个工具写清“做什么、什么时候用、什么时候不用、参数例子、常见错误”；描述也要版本化。
2. 原生工具调用（function calling）：只允许选白名单内的工具；选择结果仍交给 `ToolRuntime` 做权限、范围、参数校验。
3. 工具很多时的做法：先按问题检索出最相关的若干个工具描述，再交给模型选；比较“全部给模型”和“检索后再给”在准确率和 token 上的差别。
4. 失败处理：工具名不存在、参数错、工具超时、结果为空，分别对应“修复一次 / 换工具 / 结束并说明限制”，次数有上限。
5. 评测：工具选择准确率、参数一次通过率、平均调用次数；与现有固定路由对比。
- 生产级要点：在高风险数据场景里，用代码定路线、模型只出结构化意图，往往比完全自主更可靠；选哪种要用数据说话。
- 检查题：模型连续两次选错工具，系统应该怎么做？为什么不能无限让它重试？

### 7.3 记忆落地

## 阶段 7.5：提示词工程

出口门槛：所有提示词有版本号；每次修改都有 2.5 评测的改前 / 改后数值。

1. 版本化：提示词集中管理，记录版本号；任务追踪（trace）里能看到用的是哪个版本。
2. 结构化输出：在服务商支持的前提下，从 `json_object` 升级到按 JSON Schema 严格约束；保留 Pydantic 事后校验作为兜底。
3. 精简：删掉重复规则（例：Planner 提示词里 action 的取值写了两遍），比较 token 和路由准确率。
4. 示例选择：比较“不给示例 / 固定示例 / 按问题检索相似示例”三种做法。
5. 修复提示词：每种错误码对应一条明确的修复指引（已有 `build_planning_repair_prompt`），统计修复一次通过率。
- 学习点：提示词是需要测试的代码，不是一次写好就不管的文案。
- 检查题：删掉一条规则后 token 少了 10%、路由准确率下降 2%，你怎么决定？
